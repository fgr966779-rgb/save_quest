# Detailed Project Analysis Report: PiggyVault (June 2026)

## 1. Executive Summary
PiggyVault has successfully transitioned from MVP to a feature-rich gamified savings application. The core loop (Deposit -> XP -> Rewards) is functional and visually engaging. However, the project faces significant architectural scaling challenges, primarily due to hardcoded logic for financial goals and a "God Object" service managing the main transaction flow.

## 2. Architectural Overview
*   **Framework:** Flutter 3.6.2
*   **State Management:** Riverpod 2.6.1. Provides excellent reactivity but logic is increasingly concentrated in a few Notifiers.
*   **Database:**
    *   **Drift (SQLite):** Handles relational data (Goals, Deposits, User Profiles). Schema version 8.
    *   **Hive:** Handles key-value settings and ephemeral data (Settings, Quests, Notifications).
*   **Navigation:** GoRouter 14.8.1. Declarative and clean.
*   **AI Integration:** OpenRouter (DeepSeek). Used for "Cyber-Coach" insights and daily "Bounties".

## 3. Technical Debt & Critical Issues

### 3.1 Hardcoded N-Goals (High Priority)
The application is strictly limited to exactly two goals, identified as `goal_a` and `goal_b`. This limitation is pervasive:
*   **Database:** `Deposits` table has explicit `goalAAmount` and `goalBAmount` columns.
*   **Services:** `SavingsNotifier` and `BackupService` (CSV export) have hardcoded logic for two goals.
*   **UI:** `DashboardScreen`, `DepositScreen`, `AnalyticsScreen`, and `HistoryScreen` all assume a two-goal layout (e.g., `DualProgressRing`, `SplitSlider`).
*   **Onboarding:** Separate screens (`GoalASetupScreen`, `GoalBSetupScreen`) for each goal.

### 3.2 SavingsNotifier "God Object" (Medium Priority)
The `SavingsNotifier.createDeposit` method is a high-complexity function (~250 lines) that orchestrates:
1.  Database transactions for savings.
2.  XP and Level-up calculations.
3.  Streak management.
4.  Lootbox drop logic.
5.  Achievement validation.
6.  Social (Squad) updates.
This makes the code difficult to test, maintain, and extend without side effects.

### 3.3 Code Duplication (Low/Medium Priority)
*   **Onboarding:** `GoalASetupScreen` and `GoalBSetupScreen` are nearly identical copies.
*   **BackupService:** Manual JSON serialization/deserialization for every Drift table and Hive setting, leading to a large, fragile class that must be updated whenever the schema changes.

### 3.4 AI Integration Fragility (Medium Priority)
The `BountyNotifier` uses string manipulation and regex to extract JSON from LLM responses. If the LLM includes preamble or conversational text, parsing frequently fails, triggering a fallback.

## 4. Quality Assurance Status
*   **Linter:** 11 active warnings (mostly `use_build_context_synchronously` and `unused_local_variable`).
*   **Testing:** Minimal. `test/widget_test.dart` only verifies that the `ProviderScope` compiles. There are no unit tests for critical business logic (XP math, streak logic, database migrations).
*   **Formatting:** Inconsistent line lengths and some trailing commas missing.

## 5. Phase 2 Recommendations

1.  **Relational Goal Refactor:**
    *   Introduce a `DepositAllocations` table to link one deposit to N goals.
    *   Migrate data and remove `goalAAmount`/`goalBAmount` from the `Deposits` table.
2.  **Service Decomposition:**
    *   Move XP and Leveling logic to `XpService`.
    *   Move reward/achievement logic to a dedicated `RewardService`.
3.  **UI Generalization:**
    *   Refactor `DepositScreen` and `DashboardScreen` to iterate over a list of goals rather than accessing A and B by ID.
    *   Consolidate onboarding into a single multi-step setup flow.
4.  **Robust AI Parsing:**
    *   Implement better JSON cleaning and validation for LLM responses.
5.  **Test-Driven Refactoring:**
    *   Add unit tests for `StreakService` and `XpService` before refactoring them.
