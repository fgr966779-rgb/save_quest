# Полный отчет по анализу проекта PiggyVault (Июль 2026)

## 1. Архитектурный обзор
Проект PiggyVault представляет собой мобильное приложение для управления финансами с элементами геймификации, построенное на Flutter.

*   **State Management:** Используется **Riverpod**. Это современный выбор, обеспечивающий хорошую тестируемость и разделение состояния. Однако, наблюдается высокая концентрация логики в одном провайдере (`SavingsNotifier`).
*   **Хранение данных:**
    *   **Drift (SQLite):** Для структурированных данных (транзакции, цели, профиль). Текущая версия схемы: **8**.
    *   **Hive:** Для легковесных настроек и кеширования (сессии, квесты, ключи API).
*   **Навигация:** **GoRouter**. Реализована декларативная навигация.
*   **Стиль кода:** Проект следует принципам Feature-first архитектуры (`lib/features/`), но границы между слоями (Data/Domain/Presentation) иногда размыты.

## 2. Критический технический долг

### 2.1 Проблема N-Goals (Жесткая привязка к 2 целям)
Это самая серьезная архитектурная проблема проекта.
*   **Локализация:** В БД (`Deposits`) жестко прописаны колонки `goalAAmount` и `goalBAmount`.
*   **Бизнес-логика:** `SavingsNotifier` и `AchievementService` оперируют идентификаторами `'goal_a'` и `'goal_b'`.
*   **Интерфейс:** Слайдеры распределения и экраны онбординга (`GoalASetupScreen`, `GoalBSetupScreen`) созданы только под две цели.
*   **Риск:** Добавление третьей цели потребует переписывания ~100+ мест в коде и миграции таблиц БД.

### 2.2 God Object: SavingsNotifier
Класс `SavingsNotifier` в `lib/core/providers/savings_notifier.dart` выполняет слишком много функций:
*   Создание депозитов и обновление балансов.
*   Расчет XP (Hacker, Magnate, Resilience).
*   Управление стриками и логикой "заморозки".
*   Проверка левел-апов.
*   Генерация лутбоксов.
*   Валидация достижений.
*   Интеграция с Daily Quests и Bounty.
**Последствие:** Код сложно тестировать и поддерживать. Любая ошибка в расчете XP может сломать запись транзакции в БД.

### 2.3 Дублирование кода в Onboarding
Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` практически идентичны.
**Рекомендация:** Объединить в один переиспользуемый `GoalSetupScreen(index: n)`.

## 3. Риски и надежность

### 3.1 Хрупкий парсинг AI-ответов
Сервисы `OpenRouterService` и `PriceAnalysisService` используют текстовые промпты для получения JSON от ШИ (DeepSeek).
*   **Проблема:** Парсинг выполняется через `indexOf('{')` и регулярные выражения. Если ШИ добавит вводный текст или изменит структуру, приложение упадет или выдаст ошибку.
*   **Рекомендация:** Использовать JSON Schema (если поддерживается провайдером) или более надежные библиотеки валидации данных на стороне Dart (например, `zod` аналоги или `json_serializable` с проверкой типов).

### 3.2 Локализация (L10n)
Файл `lib/core/providers/l10n.dart` содержит огромную хардкод-карту `_localizedValues`.
*   **Проблема:** Это затрудняет работу переводчиков и увеличивает размер основного бинарного файла. Отсутствует поддержка плюрализации и сложных форматов дат.
*   **Рекомендация:** Перейти на стандартные `.arb` файлы и `flutter_localizations`.

### 3.3 Тестирование
В проекте всего один файл тестов `test/widget_test.dart`, который проверяет только базовую компиляцию провайдеров.
*   Критическая логика расчета XP и стриков не покрыта юнит-тестами в достаточной мере.

## 4. Готовность к Фазе 2 (Social & Cloud)

Текущее состояние приложения оценивается как **"частично готово"**:
1.  **UUID:** Большинство таблиц используют UUID, что отлично для синхронизации.
2.  **Schema 9:** Необходимо внедрить поля `updated_at` и `is_synced` для реализации Offline-first синхронизации.
3.  **Squads:** Логика альянсов сейчас чисто локальная. Для Фазы 2 потребуется вынос этой логики в Firebase/Supabase.
