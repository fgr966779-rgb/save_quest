# Полный отчет по глубокому анализу проекта PiggyVault

## 1. Обзор архитектуры
Приложение построено на современном Flutter-стеке, но демонстрирует признаки "быстрой разработки" (MVP), где архитектурная чистота была принесена в жертву скорости реализации.

*   **State Management (Riverpod):** Используется повсеместно. Архитектура следует паттерну "Notifier/Provider", что хорошо для масштабирования, но логика распределена неравномерно.
*   **Database (Drift/SQLite):** Типобезопасная БД. Текущая схема (v8) содержит жестко захардкоженные поля для целей, что является главным препятствием для масштабирования.
*   **Слой данных:** Используется Hive для простых настроек (`SettingsService`) и Drift для структурированных финансовых данных.

## 2. Глубокий анализ технического долга

### 2.1 Проблема "Божественного объекта" (God Object)
`SavingsNotifier` (`lib/core/providers/savings_notifier.dart`) стал центральным узлом всей бизнес-логики. Он одновременно отвечает за:
1.  Управление транзакциями БД.
2.  Геймификацию (XP, уровни, стрики).
3.  Выдачу наград (лутбоксы, достижения).
4.  Интеграцию с ИИ-баунти.
**Риск:** Любое изменение в логике депозитов может сломать систему достижений или расчет уровней. Сложность тестирования растет экспоненциально.

### 2.2 Жесткая привязка целей (Goal Coupling)
Система спроектирована строго под две цели.
*   **Файлы под угрозой:**
    *   `lib/data/database.dart` (схема таблиц `Deposits`).
    *   `lib/core/providers/providers.dart` (стейт онбординга).
    *   `lib/core/widgets/split_slider.dart` и `dual_progress_ring.dart` (UI компоненты).
**Вердикт:** Добавление 3-й цели потребует переписывания ~30% кодовой базы.

### 2.3 Интеграция с ИИ (OpenRouter)
Текущая реализация в `PriceAnalysisService` и `OpenRouterService` опирается на хрупкий строковый парсинг.
*   Использование `_extractJson` через `indexOf('{')` не гарантирует валидность данных, если модель вернет сложный текст или несколько JSON-объектов.
*   Отсутствует типизированная валидация схем ответов ИИ.

### 2.4 Локализация (L10n)
Реализация через `Map` в `l10n.dart` — это технический долг, который затруднит поддержку более чем двух языков и сделает невозможным использование внешних систем перевода без ручного копирования.

## 3. Проблемы масштабируемости
*   **Cloud Sync:** Текущая БД не готова к синхронизации. В таблицах отсутствуют поля `updated_at`, `is_deleted` (в некоторых) и `server_version`. Использование UUID — правильный шаг, но его недостаточно для разрешения конфликтов (CRDT).
*   **Социальные функции (Squads):** Логика отрядов заложена в БД, но расчеты XP отряда происходят локально внутри транзакции депозита, что невозможно в реальной многопользовательской среде без серверной части.

## 4. Рекомендации по развитию (Phase 2)

### 1. Рефакторинг N-Goals (Приоритет: Критичный)
*   Мигрировать таблицу `Deposits`, удалив `goal_a_amount` и `goal_b_amount`.
*   Внедрить таблицу связку `DepositAllocations`.
*   Унифицировать экраны настройки целей в один параметризованный виджет.

### 2. Декомпозиция SavingsNotifier (Приоритет: Высокий)
*   Создать `GamificationService`, который будет подписываться на поток депозитов или вызываться отдельно.
*   Вынести логику транзакций в `DepositRepository`.

### 3. Стабилизация ИИ-слоя (Приоритет: Средний)
*   Перейти на использование библиотек для валидации JSON (например, с помощью `json_serializable` и проверок типов).
*   Улучшить системные промпты для принудительного использования JSON Mode.

### 4. Подготовка к облаку (Sync Readiness)
*   Добавить во все таблицы Drift колонку `DateTime updatedAt`.
*   Реализовать "мягкое удаление" (soft delete) для всех сущностей, чтобы синхронизировать удаления между устройствами.
