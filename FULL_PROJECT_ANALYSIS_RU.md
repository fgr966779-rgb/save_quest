# Полный анализ проекта PiggyVault (Июль 2026)

## 1. Обзор архитектуры
Проект представляет собой мобильное приложение на Flutter, построенное с использованием принципов **Feature-first** архитектуры.

*   **State Management:** Riverpod. Используется для управления состоянием UI, зависимостями и бизнес-логикой.
*   **Database:** Drift (SQLite). Типобезопасный ORM для локального хранения данных. Текущая версия схемы: 8.
*   **Navigation:** GoRouter. Декларативная навигация с поддержкой редиректов (например, для онбординга).
*   **AI Integration:** OpenRouter (модель DeepSeek V3). Используется для генерации финансовых советов ("Insights") и ежедневных заданий ("Bounties").
*   **Gamification:** Комплексная система XP, уровней, стриков (серий), навыков (Skill Tree), достижений и RPG-аватаров.

## 2. Анализ технического долга и проблем

### 2.1 Ограничение масштабируемости (N-Goals) — КРИТИЧНО 🚨
Текущая архитектура жестко завязана на две цели: `goal_a` и `goal_b`.
*   **Где проявляется:**
    *   **Таблица `Deposits`**: содержит колонки `goalAAmount` и `goalBAmount`.
    *   **Таблица `Goals`**: методы обновления в `database.dart` явно ищут записи по ID 'goal_a' и 'goal_b'.
    *   **Логика**: в приложении обнаружено более **120** хардкод-ссылок на эти идентификаторы.
*   **Последствия**: Невозможность добавить 3-ю и более целей без переписывания значительной части ядра.

### 2.2 God Object: SavingsNotifier — ВЫСОКИЙ ПРИОРИТЕТ ⚠️
Класс `SavingsNotifier` (`lib/core/providers/savings_notifier.dart`) берет на себя слишком много обязанностей:
*   Управление транзакциями БД.
*   Расчет XP и уровней.
*   Обработка логики стриков и заморозки.
*   Валидация достижений.
*   Логика выпадения лутбоксов.
*   Обновление отрядов (Squads).
*   **Последствия**: Код сложно тестировать, расширять и поддерживать. Любое изменение в XP может сломать логику депозита.

### 2.3 Дублирование UI (Onboarding) — СРЕДНИЙ ПРИОРИТЕТ ⚠️
Экраны `GoalASetupScreen` и `GoalBSetupScreen` идентичны на ~95%.
*   **Различия**: Только ссылки на провайдеры состояния и тексты (Step 1/2).
*   **Последствия**: При изменении дизайна онбординга придется править два файла. При переходе к N-Goals эта схема станет неработоспособной.

### 2.4 Хрупкость парсинга ответов ИИ — СРЕДНИЙ ПРИОРИТЕТ ⚠️
В `BountyProvider` используется простая очистка строк от markdown-тегов (` ```json `) перед дешифровкой.
*   **Проблема**: Если модель ИИ вернет текст перед JSON или изменит формат, парсинг упадет (сработает fallback на 100 грн).
*   **Рекомендация**: Внедрить регулярные выражения для извлечения JSON и схемы валидации (например, с помощью `json_annotation` или ручной проверки полей).

### 2.5 Отсутствие тестов — ВЫСОКИЙ ПРИОРИТЕТ ⚠️
В проекте присутствует только **один** тест на компиляцию `ProviderScope`.
*   **Проблема**: Сложная математика XP, логика стриков (с учетом часовых поясов и заморозок) и финансовые расчеты (minor units) не покрыты Unit-тестами. Это создает высокий риск регрессий при рефакторинге.

## 3. Готовность к Фазе 2 (Social & Cloud)

### 3.1 Состояние базы данных
*   **Плюсы**: Большинство таблиц используют UUID (String) в качестве первичных ключей, что упрощает синхронизацию.
*   **Минусы**: Отсутствует поле `updatedAt` и флаг `isSynced` для реализации инкрементальной синхронизации (Last Write Wins).

### 3.2 Социальные функции (Squads/Joint Goals)
*   **Статус**: Реализован UI и локальные таблицы.
*   **Проблема**: Логика полностью локальная. Для Фазы 2 требуется внедрение сетевого слоя (Firebase/Supabase) и механизмов разрешения конфликтов при одновременных вкладах в общую цель.

## 4. Дорожная карта рефакторинга

1.  **N-Goals Migration (Шаг 1)**:
    *   Внедрить таблицу `DepositAllocations(deposit_id, goal_id, amount)`.
    *   Перевести `SavingsNotifier` на работу со списком аллокаций.
2.  **SavingsNotifier Decomposition (Шаг 2)**:
    *   Вынести логику XP в `XpService`.
    *   Вынести логику стриков в `StreakService`.
    *   Сделать `SavingsNotifier` только координатором транзакции.
3.  **UI Unification (Шаг 3)**:
    *   Создать универсальный `GoalSetupScreen(index)`.
    *   Обновить роутер для поддержки динамического количества шагов онбординга.
4.  **Test Coverage (Шаг 4)**:
    *   Покрыть `XpService` и `StreakService` Unit-тестами (минимум 80% coverage).

## Заключение
Проект имеет отличный функциональный фундамент и визуальную составляющую, но страдает от "детских болезней" MVP — хардкода и избыточной концентрации логики. Исправление N-Goals является критическим условием для дальнейшего развития.
