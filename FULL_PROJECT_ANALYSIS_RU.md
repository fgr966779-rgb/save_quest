# Полный технический анализ проекта PiggyVault (Июль 2026)

## 1. Обзор архитектуры
Проект представляет собой геймифицированное приложение для накоплений на базе Flutter.

*   **State Management:** Riverpod. Используется паттерн `StateNotifier` для управления состоянием и координации логики.
*   **Database (Relational):** Drift (SQLite). Хранит транзакции, цели, прогресс геймификации, питомцев и совместные цели.
*   **Storage (Key-Value):** Hive. Используется для настроек пользователя, локальных флагов (например, `MilestoneService`) и временных данных ШІ.
*   **Архитектурный паттерн:** Feature-first structure (`lib/features/`). Четкое разделение на `core`, `data` и `features`.

## 2. Критический технический долг

### 2.1 Проблема N-Goals (Жесткая привязка к 2 целям) 🚨
Это самое серьезное препятствие для масштабирования.
*   **Database (`database.dart`):** Таблица `Deposits` содержит колонки `goalAAmount` и `goalBAmount`. Это делает невозможным добавление третьей цели без изменения схемы.
*   **Logic (`savings_notifier.dart`):** Метод `createDeposit` и транзакционная логика жестко завязаны на `goalAPercent` и расчет двух сумм.
*   **Backup (`backup_service.dart`):** Экспорт в CSV и JSON (Backup) жестко прописывает Goal A и Goal B.
*   **UI Widgets:** `DualProgressRing` и `SplitSlider` физически отрисовывают только два элемента.
*   **Onboarding:** Два практически идентичных экрана `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` (~95% дублирования кода).

### 2.2 God Object: SavingsNotifier 🧠
Хотя часть логики (XP, Streaks) была вынесена в сервисы в июле 2026 года, `SavingsNotifier` остается "координатором всего":
*   Обработка транзакций БД.
*   Расчет параметров геймификации.
*   Валидация достижений.
*   Проверка баунти и квестов.
*   Управление аватаром.

### 2.3 Локализация (`l10n.dart`) 🌍
Приложение использует огромную карту `Map<String, Map<String, String>>` вместо стандартных `.arb` файлов. Это затрудняет поддержку, автоматический перевод и делает файл `l10n.dart` трудночитаемым.

### 2.4 Хрупкость AI-интеграции (OpenRouter) 🤖
*   **Парсинг:** В `BountyProvider` используется `replaceAll` для очистки JSON из ответа LLM. Это нестабильно и часто падает при нестандартных ответах модели.
*   **Валидация:** Отсутствует строгая валидация схем ответов AI на стороне Dart.

### 2.5 Готовность к Cloud Sync (Phase 2) ☁️
*   **ID:** Большинство таблиц используют UUID, что хорошо. Однако `UserProfiles` использует `id = 1`, что может вызвать проблемы при мультиаккаунтности или синхронизации профилей.
*   **Timestamps:** В таблицах отсутствуют колонки `updated_at` (за исключением некоторых), что критично для разрешения конфликтов по стратегии "Last Write Wins".

## 3. Дублирование кода и избыточность

1.  **Onboarding Screens:** `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart`. Должны быть заменены на один `GoalSetupScreen(index: n)`.
2.  **Achievement IDs:** В `AchievementService` логика проверок (например, `halfway_ps5`) завязана на конкретные строковые ID, что делает добавление нового контента трудоемким.
3.  **Milestone Service:** Использует Hive ключи вида `goal_a_25`, что опять же подтверждает проблему N-Goals.

## 4. Рекомендации и дорожная карта рефакторинга

### Шаг 1: Рефакторинг Базы Данных (Схема v9)
1.  Удалить `goalAAmount`, `goalBAmount` из `Deposits`.
2.  Создать таблицу `DepositAllocations(id, deposit_id, goal_id, amount)`.
3.  Добавить `updated_at` и `is_synced` во все таблицы.

### Шаг 2: Декомпозиция логики
1.  Полностью отвязать `SavingsNotifier` от конкретных имен целей. Он должен принимать `Map<String, double> goalAllocations`.
2.  Вынести валидацию достижений в фоновую задачу или отдельный `Observer`.

### Шаг 3: Унификация UI
1.  Переписать `DualProgressRing` в `MultiGoalProgressRing`.
2.  Создать универсальный `GoalSetupScreen`.
3.  Внедрить стандартные `.arb` файлы для локализации.

### Шаг 4: Усиление AI-слоя
1.  Использовать `structured output` (если поддерживается провайдером) или библиотеку для валидации JSON (например, `schemable`).
