# Полный технический анализ проекта PiggyVault (Июль 2026)

## 1. Обзор архитектуры

Проект представляет собой кроссплатформенное приложение на Flutter с использованием современных паттернов разработки.

*   **Управление состоянием:** Riverpod (StateNotifier, AsyncValue). Это обеспечивает хорошую реактивность, но наблюдается перегрузка логики в центральном контроллере.
*   **База данных:** Drift (SQLite) для реляционных данных (цели, депозиты, профиль). Схема находится на версии 8.
*   **Хранилище настроек:** Hive для простых пар ключ-значение и некоторых игровых состояний (квесты, уведомления).
*   **Навигация:** GoRouter с использованием декларативного подхода и поддержкой ShellRoute для нижней панели навигации.
*   **Геймификация:** Сложная система XP, уровней, навыков (Skill Tree) и наград, интегрированная напрямую в процесс сохранения средств.
*   **AI-интеграция:** OpenRouter (DeepSeek) для анализа цен и игровых механик (Bounties).

## 2. Глубокий анализ проблем и технического долга

### 2.1 Проблема "Божественного объекта" (God Object)
Центральный провайдер `SavingsNotifier` (lib/core/providers/savings_notifier.dart) берет на себя слишком много обязанностей:
*   Управление транзакциями БД.
*   Расчет XP и уровней.
*   Логика стриктов (серий).
*   Проверка достижений.
*   Выпадение лутбоксов.
*   Взаимодействие с баунти-системой и квестами.

**Риск:** Трудность тестирования, высокая вероятность багов при внесении изменений, сложность масштабирования.

### 2.2 Масштабируемость целей (Hardcoded N-Goals)
Текущая архитектура жестко ограничена двумя целями:
*   В таблице `Deposits` есть колонки `goalAAmount` и `goalBAmount`.
*   В `SavingsNotifier` параметры метода `createDeposit` завязаны на `goalAPercent`.
*   Виджеты `SplitSlider` и `DualProgressRing` рассчитаны строго на две цели.
*   На экранах Onboarding созданы две отдельные копии экрана настройки цели.

**Риск:** Невозможность добавить 3-ю или 4-ю цель без переписывания значительной части ядра приложения.

### 2.3 Дублирование кода (DRY Violation)
*   **Onboarding:** Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` практически идентичны.
*   **UI Компоненты:** Логика отрисовки прогресса дублируется в нескольких местах вместо использования единой дизайн-системы.

### 2.4 Хрупкость интеграции с ШИ (AI Fragility)
Сервисы `OpenRouterService` и `PriceAnalysisService` используют регулярные выражения и ручной поиск подстрок для извлечения JSON из ответов нейросети.
*   Метод `_extractJson` ищет первую `{` и последнюю `}`.
*   Метод `_toKopecks` агрессивно чистит строки.

**Риск:** При малейшем изменении формата ответа модели (например, добавление пояснительного текста или Markdown-разметки) парсинг может сломаться.

### 2.5 Проблемы локализации (L10n)
Файл `lib/core/providers/l10n.dart` содержит огромную хардкод-карту строк.
*   Не используются стандартные `.arb` файлы.
*   Отсутствует поддержка плюрализации и сложных контекстов.

**Риск:** Сложность поддержки при расширении на новые языки и риск ошибок при копировании ключей.

### 2.6 Консистентность данных
*   **UUID vs Auto-increment:** В таблице `UserProfiles` используется фиксированный ID=1, в то время как другие таблицы используют UUID. Это затруднит будущую синхронизацию.
*   **Атомарность:** Обновления в `WeeklyChallengeService` происходят вне основной транзакции `SavingsNotifier`.

## 3. Обнаруженные недочеты в UI/UX

*   **Стиль:** В коде встречаются упоминания об удалении шрифта "Orbitron", но местами сохраняется специфическая киберпанк-стилистика, которая может конфликтовать с Material 3.
*   **Темизация:** Цвета `goalA` и `goalB` захардкожены в `AppColors`, что не позволит легко менять их при динамическом создании целей.

## 4. Рекомендации по рефакторингу (Phase 2)

1.  **N-Goals Refactoring (Приоритет №1):**
    *   Миграция БД на версию 9: создание таблицы `DepositAllocations`.
    *   Обобщение виджетов `SplitSlider` для работы со списком целей.
    *   Создание универсального `GoalSetupScreen`.
2.  **Декомпозиция SavingsNotifier:**
    *   Вынос логики XP в `XpService`.
    *   Вынос логики стриктов в `StreakService`.
    *   Notifier должен только координировать вызовы сервисов.
3.  **Стандартизация L10n:**
    *   Переход на `flutter_localizations` и `.arb` файлы.
4.  **Усиление AI-слоя:**
    *   Использование `Response Format: json_object` в API (если доступно).
    *   Более строгая валидация схем через JSON-декодеры.
5.  **Подготовка к Cloud Sync:**
    *   Добавление колонок `updatedAt` и `isSynced` во все таблицы.
