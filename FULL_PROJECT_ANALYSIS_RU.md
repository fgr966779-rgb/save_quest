# Полный аналитический отчет по проекту PiggyVault (Июль 2026)

## 1. Архитектурный обзор
Проект PiggyVault построен на современном стеке Flutter с использованием следующих ключевых технологий:
*   **State Management:** Riverpod (используются StateNotifier и провайдеры на основе генераторов).
*   **Database:** Drift (SQLite) для реляционных данных и Hive для настроек пользователя.
*   **Навигация:** GoRouter с централизованной конфигурацией.
*   **Архитектурный паттерн:** Feature-first дизайн. Код разделен на `core`, `data` и `features` (gamification, onboarding, dashboard и др.).

## 2. Критические проблемы и технический долг

### 2.1 Проблема N-Goals (Жесткое кодирование целей)
Основная архитектурная проблема проекта — жесткая привязка к двум целям (`goal_a` и `goal_b`). Это пронизывает все слои приложения:
*   **БД (`database.dart`):** Таблица `Deposits` содержит колонки `goalAAmount` и `goalBAmount`.
*   **Логика (`SavingsNotifier`):** XP и распределение средств рассчитываются строго для двух идентификаторов.
*   **Backup (`BackupService`):** Экспорт в CSV и JSON завязан на статичные поля `goal_a`/`goal_b`.
*   **UI:** Виджеты `DualProgressRing` и `SplitSlider` не поддерживают динамическое количество целей.

**Рекомендация:** Нормализация БД. Создание таблицы `DepositAllocations (deposit_id, goal_id, amount)` и рефакторинг всех зависимых сервисов.

### 2.2 God Object: SavingsNotifier
Класс `SavingsNotifier` в `lib/core/providers/savings_notifier.dart` стал "Божественным объектом". Он управляет:
1. Сохранением депозитов.
2. Обновлением баланса целей.
3. Расчетом XP (Hacker/Magnate/Resilience).
4. Логикой стриков (серий).
5. Критическими ударами (crit logic).
6. Выдачей кредитов и кристаллов.
7. Генерацией лутбоксов.
8. Проверкой достижений.
9. Синхронизацией со Squads.

**Рекомендация:** Декомпозиция. Вынос логики геймификации в отдельные доменные сервисы (XPService, RewardService, StreakService), оставляя за Notifier только координацию транзакции.

### 2.3 Дублирование кода
*   **Onboarding:** Экраны `GoalASetupScreen` и `GoalBSetupScreen` идентичны на ~95%. Различаются только ключи провайдеров и текстовые метки.
*   **Backup Service:** Логика маппинга данных при импорте/экспорте повторяется для каждой таблицы вручную, что затрудняет добавление новых сущностей.

## 3. Анализ интеграции AI
Используется `OpenRouterService` (DeepSeek). Текущая реализация парсинга ответов является хрупкой:
*   **Метод `_extractJson`:** Использует поиск подстрок `{` и `}`, что может привести к ошибкам, если модель добавит пояснительный текст.
*   **Метод `_toKopecks`:** Полагается на регулярные выражения для очистки строк, что небезопасно при нестандартном форматировании чисел.

**Рекомендация:** Использовать JSON Schema для структурированного вывода (если поддерживается провайдером) или внедрить более надежную валидацию схем на стороне Dart.

## 4. Рекомендации по Phase 2 (Social & Cloud)

### 4.1 Подготовка к Cloud Sync
Для внедрения Firebase/Supabase необходимо:
1.  **UUID:** Убедиться, что все таблицы используют UUID (сейчас `UserProfiles` использует `int id = 1`).
2.  **Timestamps:** Добавить поле `updated_at` во все таблицы для разрешения конфликтов по стратегии "Last Write Wins".
3.  **Offline-first:** Реализовать флаг `is_synced` для каждой записи.

### 4.2 Squads и Совместные цели
Текущие таблицы `Squads` и `JointGoals` являются локальными заглушками. Для Phase 2 требуется:
*   Вынос логики обновлений в Real-time Database.
*   Реализация системы приглашений (Invitation Links) через Firebase Dynamic Links.

## 5. Стабильность и Окружение
*   **Тесты:** В проекте есть базовое покрытие тестами провайдеров, но отсутствуют интеграционные тесты сложной бизнес-логики (XP/Achievement validation).
*   **L10n:** Локализация реализована через огромную статичную карту в `l10n.dart`. При росте проекта это станет узким местом. Рекомендуется переход на стандартные `.arb` файлы.
