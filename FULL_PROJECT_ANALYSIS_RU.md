# Глубокий анализ проекта PiggyVault (Июль 2026)

## 1. Обзор проекта
PiggyVault — это мобильное приложение для управления личными финансами, построенное на базе Flutter с использованием Riverpod для управления состоянием и Drift для локальной базы данных. Приложение использует геймификацию в стиле киберпанк для стимулирования накоплений.

## 2. Обнаруженные архитектурные проблемы

### 🚨 2.1. Ограничение N-Goals (Жесткое кодирование двух целей)
Самая критическая проблема. Архитектура приложения жестко ограничена поддержкой ровно двух целей (`goal_a` и `goal_b`).
*   **База данных:** В таблице `Deposits` захардкожены поля `goal_a_amount` и `goal_b_amount`.
*   **Бизнес-логика:** `SavingsNotifier` и `BackupService` напрямую обращаются к этим полям.
*   **Интерфейс:** Виджеты `SplitSlider`, `DualProgressRing` и экраны онбординга продублированы или ограничены двумя параметрами.

### 🏗️ 2.2. SavingsNotifier как God Object
`lib/core/providers/savings_notifier.dart` выполняет слишком много функций:
*   Управление транзакциями базы данных.
*   Расчет XP и уровней.
*   Обработка стріков (серий).
*   Валидация достижений.
*   Вызов AI-сервисов (Bounties).
*   Обновление состояния отрядов (Squads).
Это делает код сложным для поддержки и практически невозможным для модульного тестирования.

### 🤖 2.3. Хрупкий парсинг AI-ответов
Сервисы `PriceAnalysisService` и `OpenRouterService` используют нестабильный строковый поиск и регулярные выражения для извлечения JSON из ответов ИИ. Это может привести к сбоям при малейшем изменении формата ответа модели.

### 👯 2.4. Дублирование кода в UI
Экраны `GoalASetupScreen` и `GoalBSetupScreen` являются почти идентичными копиями. Любое изменение в логике настройки целей требует правок в обоих файлах.

### ☁️ 2.5. Неготовность к облачной синхронизации
Текущая схема базы данных не содержит полей для отслеживания времени обновления (`updated_at`) и статуса синхронизации. Также некоторые таблицы используют автоинкрементные ID, что вызовет конфликты при объединении данных из разных источников.

## 3. Технический долг
*   **Тестирование:** Отсутствуют unit-тесты для критической бизнес-логики (XP, финансы).
*   **Локализация:** Используется кастомная Map в `l10n.dart` вместо стандартных `.arb` файлов, что ограничивает масштабируемость.
*   **DI:** Сервисы геймификации реализованы как статические классы, что затрудняет их замену или моканье в тестах.

## 4. Рекомендации
1.  Рефакторинг базы данных: переход к таблице аллокаций (`DepositAllocations`) для поддержки динамического количества целей.
2.  Декомпозиция `SavingsNotifier`: вынос логики XP, уровней и стріков в отдельные сервисы.
3.  Унификация UI: создание единого экрана настройки целей и динамических виджетов прогресса.
4.  Внедрение UUID и полей синхронизации во все таблицы БД.
5.  Покрытие критической логики unit-тестами.
