# Полный технический анализ проекта PiggyVault (Июль 2026)

## 1. Обзор архитектуры
Проект представляет собой мобильное приложение на Flutter для геймифицированного накопления средств.

*   **State Management:** Riverpod. Используется активно, но логика перегружена в провайдерах.
*   **Database (Структурированные данные):** Drift (SQLite). Хранит цели, депозиты, профиль пользователя, достижения.
*   **Local Storage (Настройки и метаданные):** Hive. Используется для хранения предпочтений пользователя и временных данных.
*   **AI Integration:** OpenRouter (DeepSeek). Используется для финансового коучинга и анализа цен.
*   **Navigation:** GoRouter.

## 2. Ключевые архитектурные проблемы и технический долг

### 2.1. Хардкод системы целей (N-Goals Problem)
Самая критическая проблема проекта — жесткая привязка к двум целям ("Goal A" и "Goal B").
*   **База данных (`database.dart`):** Таблица `Deposits` имеет поля `goalAAmount` и `goalBAmount`. Это делает невозможным создание 3-й цели без миграции БД.
*   **Бизнес-логика (`savings_notifier.dart`):** Метод `createDeposit` жестко рассчитывает распределение между двумя целями.
*   **Сервис бэкапов (`backup_service.dart`):** Экспорт в CSV и импорт завязаны на ID `goal_a` и `goal_b`.
*   **UI Компоненты:** Виджеты `DualProgressRing`, `SplitSlider` и экраны онбординга (`GoalASetupScreen`, `GoalBSetupScreen`) рассчитаны строго на две цели.

### 2.2. Объект-Бог (God Object) — `SavingsNotifier`
Класс `SavingsNotifier` в `lib/core/providers/savings_notifier.dart` берет на себя слишком много обязанностей:
1.  Управление транзакциями БД.
2.  Расчет XP и уровней.
3.  Логика стрик (серий).
4.  Проверка достижений.
5.  Выпадение лутбоксов.
6.  Обновление данных отрядов (Squads).
7.  Интеграция с баунти-системой и квестами.

Это делает код сложным для тестирования и поддержки.

### 2.3. Дублирование кода
*   **Онбординг:** Файлы `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` практически идентичны (дублирование логики и UI на 95%).
*   **Модели данных:** В `backup_service.dart` вручную прописана сериализация для каждой таблицы Drift, что требует ручного обновления при любом изменении схемы.

### 2.4. Хрупкая интеграция с ИИ
*   **Парсинг JSON:** В `PriceAnalysisService` и `OpenRouterService` используется ручной парсинг строк и регулярные выражения (`_extractJson`, `_toKopecks`) для извлечения данных из ответов ИИ. Это может привести к сбоям при изменении формата ответа модели.
*   **Промпты:** Используются простые текстовые вставки, что не гарантирует стабильность структуры ответа.

### 2.5. Фрагментация данных
Данные разделены между Drift (SQL) и Hive (NoSQL). При этом `BackupService` пытается объединить их в один JSON, но логика восстановления данных из Hive реализована менее надежно, чем для SQL.

## 3. Анализ покрытия тестами
Текущее покрытие тестами (`test/widget_test.dart`) является формальным и проверяет только запуск приложения. Отсутствуют Unit-тесты для:
*   Сложной логики XP (`XpService`).
*   Расчета стрик (`StreakService`).
*   Транзакций в `SavingsNotifier`.

## 4. Рекомендации

1.  **Рефакторинг БД:** Перейти от полей `goalAAmount/goalBAmount` к таблице `DepositAllocations`, которая связывает депозит с неограниченным количеством целей.
2.  **Декомпозиция `SavingsNotifier`:** Вынести логику геймификации в отдельные доменные сервисы (`XpDomainService`, `AchievementDomainService`), оставив нотификатору только координацию.
3.  **Унификация UI:** Создать единый `GoalSetupScreen`, принимающий параметры, вместо дублирования экранов.
4.  **Стандартизация ИИ:** Использовать структурированный вывод (Structured Output) или более надежные библиотеки для парсинга JSON.
5.  **Локализация:** Перейти с хардкодного Map в `l10n.dart` на стандартные `.arb` файлы Flutter для лучшей поддержки и перевода.
