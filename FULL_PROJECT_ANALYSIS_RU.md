# Полный отчет по анализу проекта PiggyVault (Июль 2026)

## 1. Обзор архитектуры и технологий

Проект представляет собой мобильное приложение для управления финансами с элементами геймификации, построенное на Flutter.

### Технологический стек:
*   **State Management:** Riverpod (основной инструмент управления состоянием).
*   **База данных:** Drift (SQLite) для структурированных данных (цели, транзакции, профиль).
*   **Локальное хранилище:** Hive для настроек (SettingsService) и метаданных (уведомления, квесты).
*   **Навигация:** GoRouter.
*   **AI интеграция:** OpenRouter (DeepSeek) для анализа цен и баунти.
*   **UI/Theme:** Material 3 с кастомной дизайн-системой (AppTheme, AppColors, AppTypography).

### Структура папок:
*   `lib/core`: Общие сервисы, виджеты, модели и утилиты.
*   `lib/data`: Слой данных (Drift DB, BackupService, Settings).
*   `lib/features`: Функциональные модули (dashboard, deposit, gamification, onboarding, settings, remote_control).

## 2. Критические проблемы и технический долг

### 2.1. Хардкод целей (N-Goals Problem) — КРИТИЧЕСКОЕ 🚨
Самая большая архитектурная проблема проекта — жесткая привязка к двум целям (`goal_a` и `goal_b`).
*   **База данных:** В таблице `Deposits` поля `goalAAmount` и `goalBAmount` прописаны жестко.
*   **SavingsNotifier:** Логика создания депозита (`createDeposit`) и распределения средств завязана на два фиксированных значения.
*   **AchievementService:** Проверка условий достижений (`halfway_ps5`, `halfway_monitor`) использует статические ID.
*   **UI:** Виджеты `DualProgressRing` и `SplitSlider` рассчитаны строго на две цели. Экран `Dashboard` явно ищет `goal_a` и `goal_b`.
*   **BackupService:** Экспорт в CSV и JSON учитывает только эти две цели.

### 2.2. Дублирование кода — ВЫСОКОЕ ⚠️
*   **Onboarding:** Экраны `GoalASetupScreen` и `GoalBSetupScreen` идентичны на 95%. Отличаются только ключи провайдеров и текстовые метки.
*   **Services:** В `BackupService` методы `_insertGoals`, `_insertDeposits` и т.д. содержат много повторяющегося бойлерплейта ручного маппинга JSON.

### 2.3. God Object (SavingsNotifier) — СРЕДНЕЕ ⚠️
`SavingsNotifier` берет на себя слишком много обязанностей:
*   Управление транзакциями БД.
*   Расчет XP и уровней.
*   Логика стриктов и заморозки.
*   Проверка достижений.
*   Обновление квестов и баунти.
Это затрудняет тестирование и нарушает принцип единственной ответственности.

### 2.4. Фрагментация данных — НИЗКОЕ ℹ️
Данные распределены между Drift и Hive. Например, профиль пользователя и XP лежат в Drift, а настройки темы и квесты — в Hive. При облачной синхронизации (Фаза 2) это потребует сложной координации.

### 2.5. Локализация (L10n) — НИЗКОЕ ℹ️
Использование огромной Map в `l10n.dart` вместо стандартных ARB-файлов усложняет поддержку и делает невозможным использование стандартных инструментов Flutter для перевода.

## 3. Анализ сервисов и функционала

*   **Remote Control:** Интересная фича для управления ПК через WebSocket. Реализована в отдельном модуле, выглядит автономно.
*   **Gamification:** Глубокая проработка (Skill Tree, Pets, Avatar Builder, Lootboxes). Однако многие механики (XP, навыки) реализованы как статические методы, что мешает внедрению зависимостей.
*   **AI Analysis:** Сервис `PriceAnalysisService` использует регулярные выражения для парсинга JSON от нейросети. Это хрупкое решение, которое может сломаться при небольшом изменении формата ответа.

## 4. Рекомендации по развитию (Фаза 2)

### Шаг 1: Рефакторинг N-Goals (Приоритет 1)
1.  Изменить схему БД: создать таблицу `DepositAllocations` (связь Many-to-Many между депозитами и целями).
2.  Унифицировать экраны Onboarding: создать один `GoalSetupScreen`, принимающий параметры или индекс цели.
3.  Сделать виджеты прогресса динамическими (список колец вместо `DualProgressRing`).

### Шаг 2: Декомпозиция SavingsNotifier (Приоритет 2)
1.  Вынести расчет XP в `XpService` как полноценный сервис (не статический).
2.  Вынести логику достижений в `AchievementManager`.

### Шаг 3: Подготовка к Sync (Приоритет 3)
1.  Добавить поля `updatedAt` и `isDeleted` (soft delete уже есть для депозитов) во все таблицы.
2.  Убедиться, что все ID — это UUID (сейчас в `UserProfiles` используется `id: 1`).

### Шаг 4: Инфраструктура
1.  Перейти на ARB-файлы для локализации.
2.  Усилить покрытие тестами бизнес-логики (сейчас тесты только на компиляцию провайдеров).

---
**Итог:** Проект имеет отличный функционал и визуал, но "уперся" в ограничения архитектуры MVP. Для дальнейшего масштабирования (более 2-х целей, облако) необходим глубокий рефакторинг ядра.
