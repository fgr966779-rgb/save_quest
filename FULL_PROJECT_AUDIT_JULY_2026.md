# Comprehensive Project Audit Report: PiggyVault (SaveQuest)

**Date:** July 2026
**Status:** MVP Complete / Phase 2 Preparation

## 1. Executive Summary
The PiggyVault project has successfully reached its MVP milestone, featuring a highly gamified personal finance experience with unique features like AI coaching and remote PC control. However, the project has accumulated significant technical debt, primarily centered around a hardcoded two-goal architecture ("N-Goals debt") and a "God Object" coordinator (`SavingsNotifier`). Resolving these issues is critical before proceeding with Phase 2 (Social Features, Cloud Sync).

## 2. Architectural Analysis

### 2.1 State Management (Riverpod)
- **Strengths:** Robust and reactive. Good use of `StreamProvider` for database observation.
- **Weaknesses:** Business logic is overly concentrated in `SavingsNotifier`. Some UI components directly manipulate state instead of using dedicated services.

### 2.2 Data Layer (Drift & Hive)
- **Drift (SQL):** Schema version 8 is stable but non-scalable. The `Deposits` table contains `goalAAmount` and `goalBAmount` columns, which is the root of the N-Goals debt.
- **Hive (KV):** Used for settings, notifications, and game state. This results in fragmented storage; some data should arguably be in SQLite (e.g., quests, milestones).

### 2.3 Business Logic (The God Object)
- `SavingsNotifier` handles transactions, XP, levels, streaks, rewards, and achievement validation.
- **Risk:** High complexity, difficult to unit test, and prone to side-effect bugs during modification.

## 3. Technical Debt Inventory

### 3.1 N-Goals Hardcoding (Critical 🚨)
- **Files Affected:** `lib/data/database.dart`, `lib/core/providers/savings_notifier.dart`, `lib/core/widgets/split_slider.dart`, `lib/core/widgets/dual_progress_ring.dart`, and multiple screens.
- **Impact:** Blocks users from creating more than two goals. Requires a major schema migration.

### 3.2 UI Code Duplication (Medium ⚠️)
- **Files:** `goal_a_setup_screen.dart` vs `goal_b_setup_screen.dart`.
- **Impact:** Increased maintenance effort. Any change to onboarding UI must be applied twice.

### 3.3 Static Localization (Medium ⚠️)
- **Files:** `lib/core/providers/l10n.dart`.
- **Impact:** Hard to scale. Lacks support for pluralization and gender-specific translations.

### 3.4 Sync Readiness (High 🛠️)
- **Issues:** Lack of `updatedAt` and `isSynced` flags in Drift tables. Reliance on auto-increment IDs for `UserProfiles` (id: 1).
- **Impact:** Cloud synchronization will lead to data conflicts and overwrites.

## 4. Integration Audit

### 4.1 AI Coaching (OpenRouter)
- **Status:** Functional.
- **Optimization:** Current prompts are text-only. Transitioning to JSON-mode/Structured Output would allow for more automated features (e.g., "AI-suggested deposit" with a one-click button).

### 4.2 Remote Control
- **Status:** High performance (~22 FPS).
- **Security:** Hardcoded password in `server.js` is a security risk for production deployment.

## 5. Phase 2 Roadmap & Recommendations

### Phase 2.1: Foundations (Infrastructure)
1.  **Database Migration (v9):** Introduce `DepositAllocations` table (Many-to-Many). Add `updatedAt` and `isSynced` columns.
2.  **N-Goals Refactoring:** Update `SavingsNotifier` and UI widgets to support dynamic lists of goals.
3.  **UI Consolidation:** Merge onboarding screens into a single generic template.

### Phase 2.2: Decoupling (Maintenance)
1.  **Service Extraction:** Move XP and Achievement logic out of `SavingsNotifier` into separate Riverpod Notifiers.
2.  **Testing:** Implement unit tests for `XpService`, `StreakService`, and `MilestoneService`.

### Phase 2.3: Connectivity
1.  **Cloud Sync:** Implement "Offline First" synchronization using Firebase or Supabase.
2.  **Social (Squads):** Transition local `Squads` and `JointGoals` logic to the network layer.
