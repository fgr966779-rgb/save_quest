# Полный аудит и технический анализ проекта PiggyVault (Июль 2026)

## 1. Архитектурный обзор
Проект представляет собой мобильное приложение на Flutter 3.6.2 с использованием современных подходов к разработке:
*   **Управление состоянием (State Management):** Riverpod. Состояние распределено между небольшими провайдерами и крупными `Notifier` (например, `SavingsNotifier`).
*   **База данных (Persistence):**
    *   **Drift (SQLite):** Используется для структурированных данных (цели, депозиты, профили, достижения).
    *   **Hive:** Используется для простых настроек, локализации и кеширования (настройки, уведомления, MilestoneService).
*   **Навигация:** GoRouter с централизованной конфигурацией в `app_router.dart`.
*   **Интеграция с ИИ:** OpenRouter (DeepSeek) для генерации финансовых советов и игровых заданий (баунти).

## 2. Выявленные проблемы и технический долг

### 2.1 "God Object" в SavingsNotifier (Критично 🚨)
Файл `lib/core/providers/savings_notifier.dart` содержит метод `createDeposit`, который превратился в процедурный блок объемом более 170 строк. Он одновременно управляет:
*   Записью в БД.
*   Расчетом XP и множителей.
*   Логикой "критических ударов".
*   Проверкой стрик-серий.
*   Валидацией достижений.
*   Дропом лутбоксов.
*   Обновлением данных отряда (Squads).
**Рекомендация:** Декомпозировать логику в отдельные доменные сервисы (XpCalculator, AchievementValidator, RewardService).

### 2.2 Жесткое ограничение N-Goals (Критично 🚨)
Текущая архитектура базы данных в `lib/data/database.dart` жестко привязана к двум целям:
*   В таблице `Deposits` есть колонки `goalAAmount` и `goalBAmount`.
*   Методы `saveDepositAndUpdateGoals` и `softDeleteDepositAndUpdateGoals` принимают только дельты для Цели А и Цели Б.
*   Это делает невозможным добавление 3-й цели без изменения схемы БД и переписывания бизнес-логики.
**Рекомендация:** Рефакторинг таблицы `Deposits` с выносом аллокаций в промежуточную таблицу `DepositAllocations`.

### 2.3 Дублирование кода в Onboarding (Высокий приоритет ⚠️)
Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` идентичны на ~90%. Они используют разные провайдеры для сохранения данных, но логика и UI полностью дублируются.
**Рекомендация:** Объединить в один универсальный `GoalSetupScreen(goalId: 'a'|'b')`.

### 2.4 Хрупкий парсинг ИИ-ответов (Средний приоритет ⚠️)
В `BountyProvider` и `OpenRouterService` используется строковая манипуляция для извлечения JSON из ответов ИИ. Это может привести к сбоям, если модель вернет лишний текст или другой формат.
**Рекомендация:** Использовать более строгую валидацию JSON-схемы или библиотеку для парсинга структурированных данных.

### 2.5 Локализация (Средний приоритет ⚠️)
Файл `lib/core/providers/l10n.dart` содержит огромную hardcoded карту переводов. При масштабировании на 5+ языков это станет невозможно поддерживать.
**Рекомендация:** Перейти на стандартные ARB-файлы (flutter_localizations).

## 3. Готовность к Фазе 2 (Social & Cloud Sync)

### 3.1 Состояние Squads и Joint Goals
*   Реализован UI и локальные таблицы Drift.
*   **Проблема:** Отсутствует сетевой слой. Текущие Joint Goals работают только локально, что противоречит их социальной сути.
*   **Проблема:** База данных (версия 8) все еще использует автоинкрементные ID в `UserProfiles`, что вызовет конфликты при синхронизации.

### 3.2 Поддержка Cloud Sync
*   Таблицы не содержат полей `updatedAt` и `isSynced`.
*   Необходимо внедрить UUID для всех сущностей (частично сделано, но требует проверки).

## 4. Результаты статического анализа
*   **Linter:** Выявлено 11 предупреждений (в основном `use_build_context_synchronously` и неиспользуемые переменные).
*   **Тесты:** Покрытие минимальное (проверяется только компиляция ProviderScope).

## 5. Итоговое резюме
Проект обладает мощным функционалом (система классов, дерево навыков, удаленное управление ПК), но страдает от архитектурной ригидности в ядре (N-Goals) и переусложнения центральных провайдеров. Для успешного запуска Фазы 2 требуется предварительный этап рефакторинга "базиса".
