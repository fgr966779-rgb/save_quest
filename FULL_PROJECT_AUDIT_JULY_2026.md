# Full Project Technical Audit & Analysis (July 2026)

## 1. Project Overview
PiggyVault (SaveQuest) is a gamified savings application built with Flutter. It combines financial tracking with RPG elements like classes, skills, XP, and streaks.

### Tech Stack:
- **Framework:** Flutter 3.6.2
- **State Management:** Riverpod (StateNotifier, StreamProvider)
- **Database:** Drift (SQLite) for transactional data, Hive for settings/milestones
- **Navigation:** GoRouter (declarative)
- **AI Integration:** OpenRouter (DeepSeek)

## 2. Identified Technical Debt & Architectural Bottlenecks

### 2.1. The "N-Goals" Scalability Problem (Critical) 🚨
The application is currently hardcoded to support exactly two goals ("Goal A" and "Goal B").
- **Database level:** The `Deposits` table in `database.dart` has explicit columns `goalAAmount` and `goalBAmount`.
- **UI level:** Core widgets like `DualProgressRing` and `SplitSlider` are hardcoded for two inputs.
- **Logic level:** `SavingsNotifier.createDeposit` expects `goalAPercent` and calculates Goal B as the remainder.
- **Impact:** Adding a 3rd goal requires a full database migration and refactoring of ~120 code references.

### 2.2. "God Object": SavingsNotifier ⚠️
The `SavingsNotifier` class in `lib/core/providers/savings_notifier.dart` is overloaded with responsibilities.
- The `createDeposit` method (~170 lines) handles DB persistence, XP calculation, level-ups, streak logic, achievement validation, lootbox drops, and squad updates.
- **Risk:** High complexity makes it prone to bugs and difficult to write unit tests for.

### 2.3. UI Duplication: Onboarding Setup 📋
- `goal_a_setup_screen.dart` and `goal_b_setup_screen.dart` are ~95% identical.
- **Recommendation:** Merge into a single reusable `GoalSetupScreen`.

### 2.4. Non-Standard Localization 🌐
- `lib/core/providers/l10n.dart` uses a massive hardcoded `Map`.
- **Impact:** This doesn't leverage standard Flutter ARB tools, lacks type safety, and will become a merge conflict nightmare as the app grows.

### 2.5. Fragile AI Integration 🤖
- `BountyProvider` and `OpenRouterService` rely on string-based JSON extraction (`replaceAll('```json', ...)`).
- **Risk:** LLMs often include conversational filler that can break `jsonDecode` if the regex-like cleaning fails.

## 3. Phase 2 (Social & Cloud) Readiness Assessment

### 3.1. Conflict Resolution (Sync)
- **Status:** Not Ready.
- **Gap:** All tables lack `updatedAt` (DateTime) and `isSynced` (bool) columns. Without these, implementing "Last Write Wins" or delta-syncing with a backend (Firebase/Supabase) is impossible.

### 3.2. Primary Keys
- **Status:** Mostly Ready.
- **Note:** Most tables use UUIDs (`text`), which is good. However, `UserProfiles` uses a hardcoded integer `id = 1`, which needs to change to a UUID to support multi-user syncing.

### 3.3. Social Features (Squads)
- **Status:** UI/Local DB Only.
- **Gap:** The `Squads` and `JointGoals` logic exists in the database but has no network layer. It is currently a local simulation.
