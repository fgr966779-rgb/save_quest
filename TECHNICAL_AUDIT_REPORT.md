# Technical Audit & Analysis Report: PiggyVault (June 2026)

## 1. Executive Summary
PiggyVault has successfully transitioned from a prototype to a functional gamified savings application. However, the current architecture contains significant bottlenecks that prevent scaling (specifically the N-Goals feature) and complicate data integrity (Drift/Hive fragmentation).

## 2. Architectural Analysis

### 2.1 State Management (Riverpod)
*   **Current State:** Heavy reliance on `SavingsNotifier` as a "God Object".
*   **Problem:** `createDeposit` handles ~250 lines of logic across 10+ domains (XP, Streaks, Achievements, Lootboxes, Squads, Bounties, Quests).
*   **Risk:** Extremely difficult to test in isolation and high risk of regressions during Phase 2.

### 2.2 Data Persistence (Drift vs. Hive)
*   **Drift (SQLite):** Handles core entities (Goals, Deposits, UserProfile).
*   **Hive (Key-Value):** Handles settings, milestones, notifications, weekly challenges, and goal dependencies.
*   **Fragmentation Issues:**
    *   **Atomicity:** Cannot perform atomic transactions across both stores. A deposit might save in Drift, but a milestone might fail to mark as celebrated in Hive.
    *   **Sync Complexity:** Requires two different sync strategies for Cloud implementation.
    *   **Backup:** `BackupService` manually merges data from both sources, which is error-prone.

## 3. Technical Debt & Issues

### 3.1 The "Two-Goal" Constraint (Critical)
*   **Findings:** The string `goal_a` and `goal_b` is hardcoded in **50+ locations** across the UI, logic, and database queries.
*   **Database:** `Deposits` table has hardcoded `goalAAmount` and `goalBAmount` columns.
*   **UI:** `AnalyticsScreen`, `HistoryScreen`, and `DepositScreen` use explicit logic for only two goals.

### 3.2 Reward System Fragmentation
*   **Findings:** Achievements are tracked in a dedicated Drift table (`UnlockedAchievements`), while Badges are stored in a JSON string within the `UserProfiles` table (`avatarConfig`).
*   **Constraint:** This makes it difficult to query all rewards or display a unified "Hall of Fame".

### 3.3 UI Technical Debt
*   **Findings:** 26+ hardcoded hex colors (e.g., `#00E5FF`, `#FF007F`) exist outside of `AppColors.dart`, primarily in the Avatar Builder and Onboarding screens.
*   **Linter:** 11 minor issues remaining, including `use_build_context_synchronously`.

## 4. Phase 2 Recommendations

### 4.1 N-Goals Refactoring (Priority 1)
**Proposed Schema Change:**
1.  **New Table:** `DepositAllocations`
    *   `id`: UUID (Primary Key)
    *   `deposit_id`: FK -> `Deposits.id`
    *   `goal_id`: FK -> `Goals.id`
    *   `amount`: Integer (minor units)
2.  **Migration:** Remove `goalAAmount`/`goalBAmount` from `Deposits` and move existing data to `DepositAllocations`.

### 4.2 Service Decomposition
*   **LootboxService:** Encapsulate drop rates and opening logic.
*   **RewardService:** Unify Achievement and Badge logic.
*   **QuestService:** Move quest completion triggers from the Notifier to a dedicated domain service.

### 4.3 Storage Consolidation
*   Move `Milestones` and `WeeklyChallenges` from Hive to Drift to ensure transactional integrity with deposits. Keep Hive only for ephemeral app settings.

### 4.4 Cloud Sync Readiness
*   Transition all primary keys to UUID (currently `UserProfiles` uses `Int`).
*   Add `updatedAt` timestamps to all Drift tables.
