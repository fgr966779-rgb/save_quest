# Глубокий технический анализ проекта PiggyVault (Июль 2026)

## 1. Введение
Настоящий отчет содержит результаты глубокого аудита кодовой базы PiggyVault. Анализ проводился с целью выявления архитектурных узких мест, технического долга и подготовки проекта к Фазе 2 (Social & Cloud Sync).

## 2. Архитектурный обзор
Проект построен на Flutter с использованием Riverpod для управления состоянием. Система хранения данных гибридная: Drift (SQLite) для реляционных данных и Hive для ключ-значение.

### 2.1 State Management (Riverpod)
*   **Сильные стороны:** Четкое разделение на провайдеры, использование `AsyncValue` для обработки состояний загрузки/ошибок.
*   **Слабые стороны:** Наблюдается концентрация логики в "God Object" — `SavingsNotifier`.

### 2.2 Хранение данных
*   **Drift:** Используется для целей, депозитов и профиля. Схема данных (версия 8) содержит критические ограничения.
*   **Hive:** Используется для настроек, челенджей и уведомлений. Отсутствие транзакционной целостности между Drift и Hive является риском для консистентности данных.

## 3. Выявленные проблемы и технический долг

### 3.1 Хардкод системы целей (N-Goals) 🚨
Это самая критическая проблема проекта. Система жестко завязана на существование ровно двух целей: `goal_a` и `goal_b`.
*   **Где встречается:**
    *   `lib/data/database.dart`: Колонки `goalAAmount`, `goalBAmount` в таблице `Deposits`.
    *   `lib/core/providers/savings_notifier.dart`: Ручной расчет распределения между двумя целями.
    *   `lib/core/services/gamification/achievement_service.dart`: Проверки прогресса по конкретным ID `goal_a`/`goal_b`.
    *   `lib/data/backup_service.dart`: Логика CSV/JSON экспорта жестко ожидает две цели.
    *   `lib/core/widgets/dual_progress_ring.dart` и `split_slider.dart`: Виджеты рассчитаны только на две цели.
*   **Последствия:** Невозможность создания 3-й и более целей без масштабного рефакторинга всей системы.

### 3.2 God Object: `SavingsNotifier` ⚠️
Метод `createDeposit` (~250 строк) выполняет слишком много действий:
*   Транзакции БД.
*   Математика XP (вынесена в сервис, но координация здесь).
*   Логика стриков.
*   Валидация достижений.
*   Дроп лутбоксов.
*   Обновление Squads.
*   Триггеры внешних провайдеров (Bounties, Quests).

### 3.3 Проблемы с дублированием кода
*   **Onboarding:** Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` дублируют друг друга на 90%.
*   **Services:** Логика геймификации (XP, Streaks, Achievements) частично размыта между сервисами и нотификаторами.

### 3.4 Готовность к синхронизации (Cloud Sync)
Текущая структура данных не готова к бесконфликтной синхронизации:
*   В таблицах отсутствуют колонки `updated_at`.
*   Некоторые таблицы (например, `UserProfiles`) используют `Int` в качестве первичного ключа вместо UUID.
*   Отсутствует поле `is_deleted` для многих сущностей (кроме депозитов), что затруднит синхронизацию удалений.

### 3.5 Хрупкость AI-интеграции
Использование регулярных выражений для парсинга JSON из ответов DeepSeek (`OpenRouterService`, `PriceAnalysisService`) является риском. При малейшем изменении формата ответа нейросети приложение может работать некорректно.

## 4. Рекомендации по рефакторингу

### 4.1 Приоритет 1: Динамические цели (N-Goals)
1.  **БД:** Создать таблицу `DepositAllocations (id, deposit_id, goal_id, amount)`.
2.  **БД:** Удалить `goalAAmount/goalBAmount` из `Deposits` после миграции.
3.  **UI:** Объединить экраны онбординга целей в один универсальный.
4.  **UI:** Создать универсальный виджет прогресса, поддерживающий список целей.

### 4.2 Приоритет 2: Декомпозиция нотификаторов
1.  Вынести логику транзакций геймификации из `SavingsNotifier` в отдельные доменные сервисы.
2.  Использовать паттерн "Command" или "Use Case" для сложных операций депозита.

### 4.3 Приоритет 3: Подготовка к Sync
1.  Добавить `updated_at` и `is_deleted` (soft delete) во все таблицы.
2.  Заменить все `Int` PK на `UUID`.
