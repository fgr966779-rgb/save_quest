# Глубокий анализ проекта PiggyVault (Июль 2026)

## 1. Обзор архитектуры и технологий
Проект представляет собой мобильное приложение на Flutter с элементами геймификации для управления личными накоплениями.

*   **State Management:** Riverpod.
*   **База данных:** Drift (SQLite) для реляционных данных и Hive для настроек и локального стейта.
*   **Навигация:** GoRouter.
*   **Геймификация:** Собственные сервисы для расчета XP, стриков и достижений.
*   **AI:** Интеграция с OpenRouter (модель DeepSeek) для анализа цен и финансовой помощи.

---

## 2. Ключевые архитектурные проблемы и "бутылочные горлышки"

### 2.1. Проблема "N-Goals" (Хардкод целей) — КРИТИЧНО 🚨
Самая большая архитектурная проблема проекта — жесткая привязка к двум целям (`goal_a` и `goal_b`).
*   **Где это встречается:**
    *   `lib/data/database.dart`: Таблица `Deposits` имеет колонки `goalAAmount` и `goalBAmount`.
    *   `lib/data/backup_service.dart`: Логика экспорта в CSV и JSON жестко прописывает ID целей.
    *   `lib/features/onboarding/`: Раздельные экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart`.
    *   `lib/core/providers/savings_notifier.dart`: Логика распределения средств привязана к двум переменным.
*   **Риск:** Невозможность добавить третью цель без переписывания значительной части кодовой базы.
*   **Решение:** Переход на таблицу `DepositAllocations` (связь многие-ко-многим между депозитами и целями).

### 2.2. SavingsNotifier как "God Object" 🦠
Файл `lib/core/providers/savings_notifier.dart` (метод `createDeposit`) стал слишком сложным (~250 строк в одном методе).
*   **Что он делает сейчас:**
    1.  Конвертирует валюту.
    2.  Открывает транзакцию БД.
    3.  Обновляет балансы целей.
    4.  Рассчитывает стрики (через сервис).
    5.  Считает XP (базовый, бонусный, специфический для классов).
    6.  Обрабатывает критические удары (Crit Hit).
    7.  Обновляет уровень пользователя.
    8.  Начисляет кредиты и баджи.
    9.  Обновляет XP альянса (Squads).
    10. Проверяет достижения.
    11. Генерирует лутбоксы.
*   **Риск:** Низкая тестируемость и высокая вероятность багов при внесении изменений.
*   **Решение:** Вынос логики геймификации в отдельные доменные сервисы, которые вызываются из нотификатора.

### 2.3. Фрагментация данных 🧩
Данные геймификации разбросаны по разным хранилищам:
*   `Drift`: Достижения (`UnlockedAchievements`), Скиллы (`UnlockedSkills`).
*   `Hive`: Еженедельные челенджи, уведомления.
*   `UserProfile (JSON в Drift)`: Баджи аватара, кредиты.
*   **Риск:** Нарушение атомарности обновлений. Если обновление в Drift пройдет успешно, а в Hive упадет — данные рассинхронизируются.

## 3. Анализ дублирования и избыточности

### 3.1. Экраны Onboarding
Файлы `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` практически идентичны.
*   **Решение:** Создать один универсальный `GoalSetupScreen`, который принимает индекс или конфигурацию цели.

### 3.2. Логика сериализации в BackupService
В `lib/data/backup_service.dart` используется ручное сопоставление полей для каждой таблицы Drift. При добавлении новой таблицы приходится вручную обновлять методы `_readAll`, `restoreBackup` и методы вставки.
*   **Решение:** Использование автоматической кодогенерации или более универсальных методов работы с `DataClass` от Drift.

---

## 4. Качество кода и стабильность

### 4.1. Обработка AI ответов
`PriceAnalysisService` и `BountyProvider` используют регулярные выражения для парсинга JSON из текстовых ответов нейросети.
*   **Проблема:** Если нейросеть добавит лишний текст или изменит формат, парсинг упадет.
*   **Решение:** Использование Structured Output (JsonSchema) или более надежных библиотек для валидации схем.

### 4.2. Тестовое покрытие
На данный момент проект содержит только базовый smoke-тест. Бизнес-логика (расчет XP, стриков, штрафов) не покрыта Unit-тестами. Это критично перед началом Phase 2 (Cloud Sync), так как ошибки в расчетах могут привести к повреждению данных в облаке.

## 5. План действий (Phase 2 Roadmap)

2.  **Рефакторинг SavingsNotifier:** Декомпозиция на мелкие сервисы (XpManager, StreakManager, LootboxService).
3.  **Унификация Onboarding:** Консолидация экранов настройки целей.
4.  **Подготовка к Cloud Sync:**
    *   Переход на UUID везде (сейчас `UserProfile` использует `int ID=1`).
    *   Добавление `updated_at` во все таблицы для разрешения конфликтов.
5.  **Тестирование:** Написание тестов для `StreakService` и `XpService`.
