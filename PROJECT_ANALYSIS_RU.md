# Глубокий анализ проекта PiggyVault (Июль 2026)

## 1. Архитектурный анализ и "God Objects"

### 1.1 SavingsNotifier: Центр тяжести
Основной проблемой архитектуры управления состоянием является `SavingsNotifier` (`lib/core/providers/savings_notifier.dart`). Метод `createDeposit` разросся до ~250 строк кода и выполняет слишком много задач одновременно:
- Конвертация валют (дисплейные единицы в копейки).
- Работа с транзакциями БД.
- Логика стриктов (через `StreakService`).
- Расчет XP и множителей (через `XpService`).
- Логика критических ударов.
- Управление кредитами кибер-маркета.
- Обновление конфигурации аватара.
- Проверка и разблокировка достижений.
- Работа с лутбоксами.
- Взаимодействие с другими провайдерами (`bountyProvider`, `questProvider`).

**Риски:** Высокая сложность тестирования, риск нарушения атомарности (некоторые вызовы идут вне транзакции БД), сложность внесения изменений.

### 1.2 Проблема N-Goals (Жесткое кодирование целей)
Система спроектирована с жесткой привязкой к двум целям: `goal_a` и `goal_b`. Это пронизывает все слои приложения:
- **Database:** Таблица `Deposits` имеет колонки `goalAAmount` и `goalBAmount`. В `AppDatabase` методы `saveDepositAndUpdateGoals` и `softDeleteDepositAndUpdateGoals` завязаны на ID `'goal_a'` и `'goal_b'`.
- **UI:** `DashboardScreen` и `DepositScreen` (и его стейт) напрямую ищут цели по этим ID.
- **Onboarding:** Существуют два почти идентичных экрана `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart`.
- **Backup:** `BackupService` в методе `exportCsv` жестко прописывает имена для двух целей.

**Вердикт:** Это главный архитектурный тупик, блокирующий масштабируемость. Переход к N-целям потребует серьезного рефакторинга схемы БД (таблица аллокаций).

## 2. Управление данными и готовность к облаку

### 2.1 Фрагментация хранилищ
В проекте используются две разные системы хранения:
1.  **Drift (SQLite):** Основные реляционные данные (цели, депозиты, профиль, достижения, скиллы).
2.  **Hive (Key-Value):** Настройки (`SettingsService`), уведомления, векли-челленджи и майлстоуны.

**Проблема:** Отсутствие единой транзакционности между Drift и Hive. Если обновление в Hive упадет, БД Drift может остаться в несогласованном состоянии по отношению к настройкам.

### 2.2 Первичные ключи и UUID
Большинство таблиц в Drift уже используют `text` в качестве ID и заполняются через UUID v4, что отлично для будущей синхронизации.
**Исключение:** Таблица `UserProfiles` использует `IntColumn` с фиксированным ID=1. Это не позволит хранить профили нескольких пользователей или эффективно синхронизировать их без конфликтов при смене устройства.

### 2.3 Отсутствие метаданных для синхронизации
Для реализации Фазы 2 (Cloud Sync) во всех таблицах отсутствуют критически важные поля:
- `updated_at` (для стратегии Last Write Wins).
- `is_synced` (флаг для локального отслеживания).
- `server_version` или аналоги (для более сложных стратегий слияния).

### 2.4 BackupService как технический долг
`BackupService` реализован вручную через JSON-сериализацию. При добавлении любой новой таблицы в БД или нового поля в `SettingsService`, разработчик ОБЯЗАН не забыть обновить методы импорта/экспорта в `BackupService`.
**Рекомендация:** Рассмотреть возможность автоматизации через кодогенерацию или более универсальный подход к обходу таблиц Drift.

## 3. Проблемы AI, Геймификации и Дублирования

### 3.1 Хрупкость парсинга AI-ответов
Сервисы `OpenRouterService` и `PriceAnalysisService` полагаются на текстовые промпты с требованием "вернуть только JSON". Парсинг выполняется через `_extractJson` (поиск по скобкам `{}`), что крайне нестабильно:
- Модель может добавить пояснительный текст до или после JSON.
- Любое изменение структуры ответа ломает сервис.

**Рекомендация:** Использовать JSON Schema (Structured Output) на стороне API или внедрить более надежную валидацию схем в Dart (например, через `zod` подобные библиотеки или просто строгую проверку типов).

### 3.2 Фрагментация геймификации
Логика геймификации размазана между:
- Статическими утилитами (`XpService`, `StreakService`).
- Провайдерами (`QuestProvider`, `BountyProvider`).
- "God Object" (`SavingsNotifier`).

**Проблема:** Отсутствие единого `GamificationService`, который бы инкапсулировал все бизнес-правила. Сейчас, чтобы изменить логику начисления XP, приходится править несколько файлов.

### 3.3 Дублирование UI-кода
- **Onboarding:** Экраны `GoalASetupScreen` и `GoalBSetupScreen` идентичны на 90%. Это усложняет поддержку дизайна.
- **Widgets:** Многие неоновые эффекты и карточки реализованы через `SurfaceCard`, но имеют много ручного стайлинга, который можно вынести в более высокоуровневые специализированные виджеты.

### 3.4 Локализация (l10n)
Локализация реализована через огромный хардкод-мап в `lib/core/providers/l10n.dart`.
**Минусы:**
- Файл становится огромным и нечитаемым.
- Сложность работы для профессиональных переводчиков (нет ARB/JSON файлов).
- Отсутствие поддержки плюрализации (склонение слов типа "день/дня/дней") нормальным способом.

## 4. Рекомендации и дорожная карта Фазы 2

### 4.1 Приоритет №1: Рефакторинг N-Goals
Это фундамент для всех социальных функций.
1.  **БД:** Внедрить таблицу `DepositAllocations(deposit_id, goal_id, amount)`.
2.  **Миграция:** Написать скрипт миграции, который перенесет данные из `goalAAmount/goalBAmount` в новую таблицу.
3.  **UI:** Унифицировать экраны онбординга и создать универсальный виджет выбора целей для депозита.

### 4.2 Приоритет №2: Декомпозиция SavingsNotifier
1.  Создать `Domain Services` для отдельных аспектов: `XpDomainService`, `AchievementDomainService`, `ProfileDomainService`.
2.  `SavingsNotifier` должен стать тонким координатором, который просто вызывает нужные методы сервисов внутри одной транзакции.

### 4.3 Приоритет №3: Подготовка к Cloud Sync
1.  Перевести `UserProfiles` на UUID.
2.  Добавить поля `updatedAt` во все таблицы Drift.
3.  Внедрить `SyncInterceptor` для Drift, который будет помечать измененные записи.

### 4.4 Приоритет №4: Улучшение DX (Developer Experience)
1.  Перейти на официальный механизм локализации Flutter (ARB файлы).
2.  Автоматизировать `BackupService` через рефлексию или генерацию схем.
3.  Внедрить более строгую типизацию для ответов AI.
