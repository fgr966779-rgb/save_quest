# Полный анализ проекта PiggyVault (Июль 2026)

## 1. Архитектурный обзор
Проект построен на современном стеке Flutter с использованием следующих решений:
*   **Управление состоянием:** Riverpod (StateNotifier).
*   **База данных:** Drift (SQLite) для структурированных данных и Hive для простых настроек.
*   **Архитектура:** Попытка следования Clean Architecture, но с сильным уклоном в сторону "God Object" в слое провайдеров.
*   **Геймификация:** Развитая система XP, уровней, стриков и достижений.

---

## 2. Критический технический долг

### 2.1 Проблема N-Goals (Самая критичная) 🚨
Логика приложения жестко завязана на существовании ровно двух целей: "Goal A" и "Goal B".
*   **База данных:** В таблице `Deposits` захардкожены колонки `goalAAmount` и `goalBAmount`. Это делает невозможным добавление третьей цели без изменения схемы БД и всей бизнес-логики.
*   **SavingsNotifier:** Метод `createDeposit` принимает `goalAPercent`, а остаток автоматически уходит в `goal_b`.
*   **UI:** Виджеты `DualProgressRing` и `SplitSlider` рассчитаны только на два значения.
*   **Достижения:** В `AchievementService` проверки завязаны на ID `goal_a` и `goal_b`.

**Рекомендация:** Переход на таблицу `DepositAllocations` (связь many-to-many между депозитами и целями).

### 2.2 SavingsNotifier как God Object 🏗️
`SavingsNotifier` (lib/core/providers/savings_notifier.dart) берет на себя слишком много:
1.  Конвертация валют.
2.  Запись в БД.
3.  Расчет XP и уровней.
4.  Логика стриков (частично вынесена, но координация тут).
5.  Логика критических ударов.
6.  Выдача лутбоксов.
7.  Валидация достижений.
8.  Обновление конфига аватара.

**Рекомендация:** Разделение на мелкие Domain Services (XpCalculator, LootboxService, TransactionCoordinator).

## 3. Анализ дублирования

### 3.1 Onboarding Screens 👥
Файлы `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` идентичны на 95%. Разница только в текстах и провайдерах, в которые сохраняются данные.
**Рекомендация:** Создать один `GoalSetupScreen(index: 0/1)` или использовать динамический список целей уже на этапе онбординга.

### 3.2 Логика достижений 🏆
Проверки типа `meetsCriteria` в `AchievementService` содержат много повторяющегося кода для разных ID наград.
**Рекомендация:** Декларативная система условий (Condition Engine), где условия хранятся в JSON или объектах, а не в массивном `switch`.

---

## 4. Проблемы сервисов и инфраструктуры

### 4.1 Хрупкий парсинг ИИ (PriceAnalysisService) 🤖
Метод `_extractJson` ищет первую `{` и последнюю `}`, что может сломаться при сложном ответе от модели. Метод `_toKopecks` использует регулярные выражения для очистки строк, что ненадежно при разных форматах вывода чисел ИИ.
**Рекомендация:** Использовать JSON Schema для структурированного вывода (Structured Output) от OpenRouter.

### 4.2 Локализация (L10n) 🌍
Вместо стандартных `.arb` файлов используется огромный Map в `lib/core/providers/l10n.dart`.
*   **Минус:** Сложно поддерживать при росте количества строк.
*   **Минус:** Нет поддержки плюрализации (например, "1 день", "2 дня", "5 дней") стандартными средствами Flutter.

### 4.3 Безопасность и API 🔑
API-ключи (OpenRouter) хранятся в `SettingsService` через Hive. Если устройство не зашифровано, ключи могут быть уязвимы.

## 5. Готовность к Cloud Sync (Phase 2)

Текущее состояние БД **не готово** к полноценной синхронизации:
1.  **Auto-increment IDs:** Таблица `UserProfiles` использует ID=1. При синхронизации нескольких устройств возникнут конфликты. Нужно переходить на UUID.
2.  **Отсутствие метаданных:** В таблицах нет колонок `updatedAt`, `isSynced` или `deletedAt` (для всех таблиц). Без этого невозможно реализовать стратегию "Last Write Wins" или дельта-обновления.
3.  **Схема данных:** Жесткая привязка к `goal_a/b` сделает невозможным совместное использование целей (Squads) в будущем, если у участников разное количество активных целей.

## 6. Резюме для продолжения разработки

**Топ-3 задачи для начала Phase 2:**
1.  **Рефакторинг БД на N-Goals:** Создание связующих таблиц и миграция данных.
2.  **Унификация UI:** Замена дублирующихся экранов онбординга на один универсальный.
3.  **Подготовка к Sync:** Добавление UUID и меток времени во все таблицы.

Проект имеет отличную базу в плане геймификации и UI-дизайна, но архитектура данных требует серьезного "фундаментального" вмешательства для дальнейшего масштабирования.
