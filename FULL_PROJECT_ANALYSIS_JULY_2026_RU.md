# Глубокий технический анализ проекта PiggyVault (Июль 2026)

## 1. Архитектурный обзор
Проект построен на современном стеке Flutter 3.6.2 с использованием **Riverpod** для управления состоянием и **Drift** (SQLite) для локального хранения данных.

### Текущая структура:
- **lib/core**: Ядро приложения — константы, общие виджеты, навигация (GoRouter), локализация (l10n) и базовые сервисы.
- **lib/data**: Слой данных — база данных Drift, настройки Hive и сервис резервного копирования.
- **lib/features**: Функциональные модули — Dashboard, Deposit, Gamification, Onboarding, Settings и Remote Control. Применен Feature-first подход.
- **remote_server**: Отдельный Node.js сервер для функционала дистанционного управления ПК.

## 2. Инвентаризация технического долга

### 2.1 Проблема "Goal A/B" (Критично 🚨)
Архитектура жестко завязана на существование ровно двух целей.
- **БД**: Таблица `Deposits` содержит колонки `goalAAmount` и `goalBAmount`. Таблица `Goals` содержит записи с захардкоженными ID `goal_a` и `goal_b`.
- **Бизнес-логика**: В `SavingsNotifier` и `AppDatabase` методы обновления баланса (например, `saveDepositAndUpdateGoals`) принимают параметры `goalADelta` и `goalBDelta`.
- **Масштабируемость**: Добавление третьей цели невозможно без изменения схемы БД и массового рефакторинга кода.

### 2.2 God Object: SavingsNotifier (Актуально ⚠️)
Метод `createDeposit` в `SavingsNotifier` представляет собой процедурный блок объемом более 170 строк. Он одновременно управляет:
1. Записью депозита в БД.
2. Расчетом XP и повышением уровней.
3. Логикой стриков (серий дней).
4. Критическими ударами (crit hits).
5. Начислением кредитов и выпадением лутбоксов.
6. Проверкой достижений и обновлением аватара.
7. Обновлением прогресса альянсов (Squads).

Это делает код крайне сложным для тестирования и поддержки. Любое изменение в логике наград может сломать базовый функционал депозитов.

### 2.3 Дублирование UI (Актуально ⚠️)
- **Onboarding**: Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` идентичны примерно на 88%. Это классическое дублирование кода, которое затрудняет изменение процесса регистрации.
- **Виджеты**: `DualProgressRing` и `SplitSlider` жестко запрограммированы на отображение двух дуг/ползунков. Они не поддерживают динамический список целей.

### 2.4 Хрупкость интеграции с ИИ (Средне ⚠️)
- **Парсинг**: `BountyNotifier` использует текстовые манипуляции (`replaceAll`, `trim`) для извлечения JSON из ответов ИИ. Это может привести к сбоям, если модель добавит пояснительный текст.
- **Валидация**: Отсутствует надежная валидация схем ответов от OpenRouter.

## 3. Анализ стабильности и тестов
- **Тестовое покрытие**: На текущий момент в проекте присутствует только один активный тест `test/widget_test.dart`, проверяющий компиляцию `ProviderScope`. Юнит-тесты для сложной логики `SavingsNotifier` отсутствуют.
- **Линтер**: В проекте осталось 11 предупреждений линтера, в основном касающихся использования `BuildContext` в асинхронных методах и неиспользуемых переменных.

## 4. План перехода к Фазе 2

### Шаг 1: Рефакторинг базы данных (N-Goals)
- Внедрение таблицы `DepositAllocations(deposit_id, goal_id, amount)`.
- Удаление жестких ссылок на `goal_a` / `goal_b` из таблицы `Deposits`.
- Миграция данных из версии 8 в версию 9.

### Шаг 2: Декомпозиция SavingsNotifier
- Вынос расчета XP в `XpDomainService`.
- Вынос логики наград в `RewardCoordinator`.
- Использование паттерна "Domain Events" для уведомления систем достижений о совершенном депозите.

### Шаг 3: Унификация UI
- Создание универсального `GoalSetupScreen`, принимающего конфигурацию для конкретного шага онбординга.
- Рефакторинг виджетов прогресса для работы со списком `List<GoalProgress>`.

### Шаг 4: Повышение надежности ИИ
- Переход на структурированный вывод (JSON mode) в запросах к OpenRouter.
- Внедрение валидаторов (например, через `json_annotation`) для входящих данных от нейросети.
