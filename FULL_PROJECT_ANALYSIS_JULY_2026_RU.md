# Полный технический анализ проекта PiggyVault (Июль 2026)

## 1. Введение
Данный отчет представляет собой глубокий анализ текущего состояния кодовой базы проекта PiggyVault. Цель анализа — выявление архитектурных ограничений, технического долга и подготовка фундамента для реализации Phase 2 (Dynamic N-Goals, Cloud Sync, Social).

---

## 2. Архитектурный обзор

### 2.1. Стек технологий
*   **Framework:** Flutter 3.6.2 (Stable).
*   **State Management:** Riverpod 2.x (с генераторами кода).
*   **Database:** Drift (SQLite) для реляционных данных, Hive для K/V настроек.
*   **Navigation:** GoRouter (с вложенной навигацией через ShellRoute).
*   **AI:** OpenRouter API (DeepSeek/GPT) для геймифицированного контента.

### 2.2. Структура проекта
Проект следует принципу **Feature-first**:
*   `lib/core/`: Ядро приложения (темы, константы, навигация, общие сервисы и виджеты).
*   `lib/data/`: Слой данных (Drift БД, SettingsService, Backup).
*   `lib/features/`: Функциональные модули (Dashboard, Gamification, Deposit, Onboarding и др.).

---

## 3. Критические архитектурные проблемы (Блокировщики)

### 3.1. Проблема "N-Goals" (Хардкод целей) 🚨
Приложение жестко ограничено поддержкой ровно двух целей. Это самый серьезный технический долг.
*   **Persistence:** Таблица `Deposits` содержит колонки `goalAAmount` и `goalBAmount`.
*   **Logic:** `SavingsNotifier.createDeposit` принимает фиксированный процент для одной цели.
*   **UI:** Виджеты `DualProgressRing` и `SplitSlider` не поддерживают списки целей.
*   **Impact:** Добавление 3-й цели невозможно без миграции БД и переписывания ~40% бизнес-логики.

### 3.2. God Object: `SavingsNotifier` ☢️
Файл `lib/core/providers/savings_notifier.dart` перегружен ответственностью. Метод `createDeposit` (~170 строк) выполняет:
1.  Транзакционную запись в БД.
2.  Расчет XP и уровней.
3.  Логику стрейков.
4.  Выдачу лутбоксов и ачивок.
5.  Обновление состояния "Сквадов".
*   **Impact:** Высокая сложность тестирования и риск регрессий при любых изменениях в геймификации.

## 4. Анализ дублирования и избыточности

### 4.1. Onboarding Duplication ⚠️
Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` идентичны на **88%** (269 строк из 304).
*   **Recommendation:** Унификация в `GoalSetupScreen(goalId: ...)`.

### 4.2. Консистентность наименований
В проекте сосуществуют два названия: **PiggyVault** и **SaveQuest**. Это может привести к путанице при релизе и брендинге.

---

## 5. Технические риски

### 5.1. Хрупкость AI-интеграции 🤖
Парсинг JSON из ответов ИИ в `BountyProvider` и `PriceAnalysisService` реализован через `replaceAll` и строковые манипуляции.
*   **Risk:** Любое отклонение ИИ от формата (вводный текст, кавычки) приведет к падению приложения.

### 5.2. Тестовое покрытие 🧪
На текущий момент в проекте **отсутствуют юнит-тесты** для критической логики (XP, Streaks, Penalty). Имеется только базовый `widget_test.dart`.

### 5.3. Синхронизация (Sync Readiness) ☁️
Несмотря на использование UUID, в таблицах отсутствуют поля `updatedAt` и `isSynced`, что необходимо для реализации стратегии "Last Write Wins" в Phase 2.

---

## 6. Рекомендации по рефакторингу (Phase 2 Roadmap)

1.  **DB Migration (v9):** Вынос аллокаций депозитов в таблицу `DepositAllocations`.
2.  **Decomposition:** Вынос геймификации из `SavingsNotifier` в отдельные `Domain Services`.
3.  **UI Unification:** Создание универсальных виджетов для работы со списками целей (вместо "Dual" компонентов).
4.  **AI Stability:** Использование JsonSchema для запросов к OpenRouter.
5.  **Quality:** Покрытие сервисов `XpService` и `StreakService` тестами перед началом рефакторинга.
