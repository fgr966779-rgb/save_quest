# Полный технический аудит и анализ проекта PiggyVault (Июль 2026)

## 1. Введение
Данный отчет представляет собой глубокий анализ текущего состояния проекта PiggyVault. Проект успешно завершил первую фазу разработки (MVP) и готов к переходу ко второй фазе (Социальные функции и Облачная синхронизация). Анализ охватывает архитектуру, стек технологий, текущую функциональность и детальный разбор технического долга.

---

## 2. Стек технологий и Архитектура

### 2.1 Технологический стек
*   **Фреймворк:** Flutter 3.x (с использованием Impeller).
*   **Язык:** Dart 3.x.
*   **Управление состоянием:** Riverpod (Notifier, StateNotifier, AsyncValue). Активно используется кодогенерация (`riverpod_generator`).
*   **База данных:**
    *   **Drift (SQLite):** Для структурированных данных (цели, депозиты, профили).
    *   **Hive:** Для легковесных настроек, кеширования и игровых данных (квесты, уведомления).
*   **Навигация:** GoRouter (декларативный подход, поддержка ShellRoute для нижнего меню).
*   **AI интеграция:** OpenRouter (DeepSeek) для анализа цен и генерации ежедневных "баунти".
*   **Локализация:** Собственная реализация на базе `StateNotifier` и статической карты строк (без ARB файлов).

### 2.2 Архитектура
Проект следует принципам **Clean Architecture** (в упрощенном виде для Flutter) с разделением на слои:
*   **Presentation:** Виджеты и Riverpod-провайдеры.
*   **Domain/Service:** Выделенные сервисы для логики (XP, Streak, Achievements).
*   **Data:** Drift database, DAO-подобные методы в классе БД, репозитории (SettingsService).

## 3. Текущая функциональность

### 3.1 Основной цикл
Пользователь устанавливает две цели (Goal A и Goal B). Каждый депозит распределяется между ними. За депозиты начисляется XP, поддерживается серия (Streak), открываются достижения.

### 3.2 Игровые механики
*   **Система уровней и XP:** Динамический расчет опыта, уровни, специфический опыт по классам (Hacker, Magnate, Resilience).
*   **Дерево навыков (Skill Tree):** Возможность разблокировки пассивных бонусов за очки навыков (SP).
*   **Стрики и Заморозка:** Механика удержания пользователя через ежедневные депозиты с использованием "токенов заморозки".
*   **Лутбоксы и Маркет:** Косметические награды и бонусы, покупаемые за внутриигровую валюту (Cyber-Credits).
*   **Питомцы (Pets):** Голографические помощники, требующие ухода (траты SP).

### 3.3 Продвинутые функции
*   **Терминал (CLI):** Интерфейс командной строки для продвинутых пользователей.
*   **Удаленное управление ПК:** Встроенный сервис для контроля рабочего стола через WebSocket.
*   **Анализ цен:** AI-сканер для проверки стоимости товаров на украинском рынке.

## 4. Глубокий анализ технического долга и проблем

### 4.1 "Hardcoded N-Goals" (Критично 🚨)
**Проблема:** Весь код жестко завязан на существование ровно двух целей: `goal_a` и `goal_b`.
*   **БД:** Таблица `Deposits` содержит колонки `goalAAmount` и `goalBAmount`.
*   **Логика:** Методы `saveDepositAndUpdateGoals` в `AppDatabase` и логика в `SavingsNotifier` явно принимают параметры для двух целей.
*   **UI:** Виджеты `SplitSlider`, `DualProgressRing` и экраны онбординга дублированы или жестко ограничены двумя элементами.
*   **Последствия:** Невозможно добавить 3-ю цель без переписывания значительной части ядра.

### 4.2 "SavingsNotifier" как God Object (Актуально ⚠️)
**Проблема:** Класс `SavingsNotifier` координирует слишком много процессов: сохранение в БД, расчет XP, валидацию достижений, проверку баунти, выполнение квестов.
*   **Рекомендация:** Продолжить декомпозицию. Часть логики уже вынесена в `XpService` и `StreakService`, но координация остается перегруженной.

### 4.3 Дублирование UI (Актуально ⚠️)
**Проблема:** Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` идентичны на 95%.
*   **Рекомендация:** Объединить в единый `GoalSetupScreen`, принимающий конфигурацию или индекс цели.

### 4.4 Хрупкость AI-парсинга (Актуально ⚠️)
**Проблема:** В `PriceAnalysisService` и `BountyProvider` используется текстовый поиск JSON в ответах AI (`_extractJson`). Это подвержено ошибкам, если AI вернет некорректный формат.
*   **Рекомендация:** Использовать JSON Schema (если поддерживается) или более надежные библиотеки для валидации схем в Dart.

### 4.5 Подготовка к облачной синхронизации (Риск ⚠️)
**Проблема:**
1. Использование автоинкрементных ID в `UserProfiles` (id: 1) не позволит объединять данные нескольких пользователей или устройств.
2. Отсутствие колонок `updatedAt` и `isSynced` во всех таблицах.
3. Отсутствие UUID в некоторых второстепенных таблицах.

## 5. Рекомендации по рефакторингу (Фаза 2)

### 5.1 Переход на динамические цели (N-Goals)
1.  **Миграция БД (Версия 9):**
    *   Удалить `goalAAmount` и `goalBAmount` из `Deposits`.
    *   Создать таблицу `DepositAllocations (deposit_id, goal_id, amount)`.
2.  **Рефакторинг провайдеров:** Обновить `SavingsNotifier.createDeposit` для приема `Map<String, double> allocations`.
3.  **Унификация UI:** Создать универсальные виджеты для списка целей с поддержкой неограниченного количества элементов.

### 5.2 Инфраструктура синхронизации
1.  Добавить `updatedAt` (DateTime) и `isSynced` (Bool) во все таблицы Drift.
2.  Перейти на UUID для всех первичных ключей.
3.  Реализовать `SyncService` для фоновой отправки изменений (Offline-first подход).

### 5.3 Улучшение локализации
Перейти с жестко заданной Map в `l10n.dart` на стандартные Flutter `.arb` файлы или внешнюю CMS, чтобы упростить поддержку и перевод.

### 5.4 Стабилизация AI
Внедрить промпты с четким требованием формата и добавить слой валидации DTO перед преобразованием в модели данных.

---

## 6. Заключение
Проект PiggyVault обладает уникальным и богатым набором функций для финансового приложения. Однако архитектурное ограничение "двух целей" и жесткая связность в базе данных являются главными препятствиями для масштабирования. Проведение рекомендованного рефакторинга позволит бесшовно внедрить облачную синхронизацию и социальные функции в Фазе 2.
