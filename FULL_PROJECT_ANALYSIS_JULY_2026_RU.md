# Полный технический анализ проекта PiggyVault (Июль 2026)

## 1. Введение
Данный отчет содержит глубокий анализ текущего состояния кодовой базы, архитектурных решений, выявленного технического долга и рекомендаций для Фазы 2 разработки.

## 2. Архитектура и Технологический стек
*   **Framework:** Flutter 3.6.2 (Dart 3.6.0)
*   **State Management:** Riverpod 2.5+ (с генераторами).
*   **Database:**
    *   Drift 2.19 (SQLite) — реляционные данные. Схема версии 8.
    *   Hive 2.2 — локальные настройки и кеш уведомлений.
*   **Navigation:** GoRouter 14.2.
*   **AI Integration:** OpenRouter (модели DeepSeek) для генерации контента.
*   **Структура:** Feature-first (`lib/features/`), разделение на `core`, `data` и `features`.

## 3. Выявленные проблемы (Технический долг)

### 3.1. Проблема "N-Goals" (Критично)
Архитектура жестко ограничена двумя целями.
- **БД:** Таблица `Deposits` содержит фиксированные колонки `goal_a_amount` и `goal_b_amount`.
- **Логика:** `SavingsNotifier` и `AppDatabase` имеют методы, принимающие ровно два дельта-значения.
- **Масштабируемость:** Добавление третьей цели потребует изменения схемы БД и переписывания ~120 мест в коде.

### 3.2. "God Object" — SavingsNotifier
Класс `SavingsNotifier` в `lib/core/providers/savings_notifier.dart` выполняет слишком много функций:
- БД-транзакции.
- Расчет XP (Experience Points).
- Логика стрик-системы.
- Шансы критического внесения (Critical Hit).
- Геймификация (лутбоксы, достижения).
- Обновление отрядов (Squads).
- Проверка баунти (Bounties).
**Риск:** Высокая сложность тестирования, хрупкость при изменениях.

### 3.3. Дублирование Onboarding UI
Экраны `GoalASetupScreen` и `GoalBSetupScreen` почти идентичны.
- Разница только в провайдерах, в которые сохраняются данные, и цветах.
- Копипаста составляет ~90% кода (около 270 строк).

### 3.4. Парсинг AI ответов
Методы в `BountyProvider` и `OpenRouterService` используют строковые манипуляции (`replaceAll('```json', '')`) для извлечения данных.
- **Риск:** Нестабильность при изменении формата ответа модели. Отсутствие строгой валидации схемы.

### 3.5. Отсутствие тестов
В проекте практически нет тестов для бизнес-логики.
- Единственный тест `widget_test.dart` проверяет только базовый запуск.
- Критически важные расчеты XP и стриков не покрыты Unit-тестами.

### 3.6. Линтер (Linter Issues)
Обнаружено 11 предупреждений, включая:
- `use_build_context_synchronously` в `dashboard_screen.dart` и `settings_screen.dart`.
- Неиспользуемые переменные и элементы (`_calculatePetLevel`, `tokensToConsume` и др.).

## 4. Рекомендации по развитию

### Фаза 2: Рефакторинг и Масштабируемость
1.  **Динамические цели:**
    - Миграция БД на версию 9.
    - Внедрение таблицы `DepositAllocations`.
    - Удаление хардкода `goal_a/b`.
2.  **Декомпозиция:**
    - Вынос логики XP в `XpService`.
    - Вынос логики стриков в `StreakService`.
3.  **Унификация UI:**
    - Создание единого `GoalSetupScreen`.
    - Обновление `SplitSlider` для работы с массивом долей.
4.  **Синхронизация:**
    - Добавление полей `updated_at` и `is_synced` во все таблицы БД.
    - Переход на UUID для всех ключей (частично выполнено).

## 5. Заключение
Проект имеет отличную визуальную составляющую и богатый функционал геймификации, но страдает от "детских болезней" MVP — хардкода и отсутствия тестов. Для перехода к социальной фазе (Squads, Cloud Sync) необходим этап технической стабилизации.
