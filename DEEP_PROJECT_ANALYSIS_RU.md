# Глубокий технический анализ проекта PiggyVault (Июль 2026)

## 1. Введение
Данный отчет представляет собой результат глубокого аудита кодовой базы PiggyVault. Цель анализа — выявление архитектурных узких мест, технического долга и подготовка фундамента для Фазы 2 разработки.

---

## 2. Архитектурный обзор
Проект построен на стеке:
- **UI:** Flutter (Material 3)
- **State Management:** Riverpod
- **Database:** Drift (реляционная) + Hive (key-value)
- **Navigation:** GoRouter

### Ключевые проблемы архитектуры:
1.  **God Object (SavingsNotifier):** Файл `lib/core/providers/savings_notifier.dart` содержит более 300 строк логики. Он отвечает за:
    - Конвертацию валют.
    - Транзакции БД.
    - Расчет XP и Стриков.
    - Логику критических ударов.
    - Выдачу лутбоксов.
    - Проверку достижений.
    - Интеграцию с баунти и квестами.
    Это нарушает принцип единственной ответственности (SRP) и затрудняет тестирование.

2.  **Хардкод N-Goals:** По всему проекту (более 120 упоминаний) жестко захардкожены идентификаторы целей `goal_a` и `goal_b`.
    - **БД:** В таблице `Deposits` есть колонки `goalAAmount` и `goalBAmount`.
    - **UI:** Виджеты `DualProgressRing` и `SplitSlider` рассчитаны строго на две цели.
    - **Onboarding:** Экраны настройки дублируются для A и B.
    - **Achievements:** Логика достижений (`AchievementService`) напрямую проверяет ID `goal_a`.

3.  **Фрагментация данных:** Данные распределены между Drift и 5+ коробками Hive. Обновления в `WeeklyChallengeService` (Hive) происходят вне транзакции Drift, что может привести к рассинхронизации данных при сбоях.

## 3. Технический долг и недочеты

### 3.1 Хрупкость интеграции с ИИ
Классы `OpenRouterService` и `PriceAnalysisService` используют регулярные выражения и ручной парсинг строк для извлечения JSON из ответов нейросети. Это высокий риск падения приложения при нестандартном ответе модели (например, если DeepSeek добавит вводный текст).

### 3.2 Проблемы BackupService
Текущий `BackupService` (`lib/data/backup_service.dart`):
- Требует ручного обновления при добавлении каждой новой таблицы.
- Логика CSV экспорта/импорта жестко привязана к двум целям.
- Использует автоинкрементные ID для профилей, что сделает облачную синхронизацию (Cloud Sync) крайне болезненной из-за конфликтов ID.

### 3.3 Дублирование кода
- **Onboarding:** `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` почти идентичны.
- **Геймификация:** XP-логика разбросана между `SavingsNotifier` и `XpService`.

## 4. Рекомендации по рефакторингу (Phase 2)

### 4.1 Переход к динамическим целям (N-Goals)
1.  **Миграция БД:**
    - Создать таблицу `DepositAllocations { deposit_id, goal_id, amount }`.
    - Удалить `goalAAmount/goalBAmount` из `Deposits`.
2.  **UI:** Рефакторинг `DualProgressRing` в `MultiGoalProgressRing`, принимающий список целей.
3.  **Onboarding:** Создать единый `GoalSetupScreen`, который вызывается циклично.

### 4.2 Декомпозиция SavingsNotifier
Необходимо выделить "Доменные сервисы":
- `XpEngine`: только математика опыта.
- `StreakEngine`: проверка и обновление серий.
- `LootboxService`: логика дропа.
`SavingsNotifier` должен стать только координатором, вызывающим эти сервисы.

### 4.3 Улучшение синхронизации
- Перейти на **UUID** для всех первичных ключей (включая UserProfile).
- Добавить колонки `updated_at` и `is_dirty` для отслеживания изменений перед выгрузкой в облако.

### 4.4 Стабилизация ИИ
- Внедрить JSON-схемы в промпты.
- Использовать более надежные библиотеки для валидации JSON (например, `json_serializable`).

---

## 5. Заключение
Проект имеет отличный функциональный фундамент, но архитектурно "зажат" в рамках двух целей и перегруженного провайдера. Реализация Фазы 2 (Squads, Cloud Sync) потребует предварительного рефакторинга описанных выше узлов.
