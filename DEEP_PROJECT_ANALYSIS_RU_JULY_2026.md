# Глубокий технический анализ проекта PiggyVault (Июль 2026)

## 1. Обзор архитектуры
Проект представляет собой мобильное приложение для накоплений с элементами геймификации, построенное на Flutter.

*   **State Management:** Riverpod. Используется для внедрения зависимостей и управления состоянием UI.
*   **Хранение данных:**
    *   **Drift (SQLite):** Реляционные данные (цели, транзакции, профиль пользователя, достижения, навыки, лутбоксы, питомцы, банды).
    *   **Hive:** Ключ-значение для настроек приложения (`SettingsService`), ежедневных квестов и уведомлений.
*   **Сервисы:** Набор специализированных классов для геймификации (XP, Streak, Achievements) и внешних интеграций (OpenRouter для ИИ).

## 2. Анализ критических проблем и технического долга

### 2.1 "God Object": SavingsNotifier
Класс `SavingsNotifier` в `lib/core/providers/savings_notifier.dart` берет на себя слишком много обязанностей. Метод `createDeposit` занимает около 250 строк и выполняет:
*   Конвертацию валют.
*   Бизнес-логику транзакций БД.
*   Расчет XP и уровней.
*   Логику критических ударов.
*   Обновление стриков.
*   Расчет наград и достижений.
*   Интеграцию с бандами (Squads).
*   Проверку Bounty и Daily Quests.

**Риск:** Высокая сложность поддержки, трудности при тестировании, риск нарушения атомарности при сбоях во внешних вызовах (например, `bountyProvider`).

### 2.2 Жестко заданные цели (N-Goals Problem)
Логика приложения завязана на существовании ровно двух целей: `goal_a` и `goal_b`. Это прослеживается в:
*   **БД:** Колонки `goalAAmount` и `goalBAmount` в таблице `Deposits`.
*   **Сервисах:** `AchievementService` и `BackupService` имеют хардкод ID целей.
*   **UI:** `DualProgressRing`, `SplitSlider` и экраны онбординга жестко ориентированы на "две цели".
*   **L10n:** Ключи локализации типа `dash_goal_a`, `dash_goal_b`.

**Риск:** Невозможность создания 3-й и более целей без масштабного рефакторинга всей системы.

### 2.3 Фрагментация данных
Данные распределены между Drift и 5-ю различными боксами Hive.
*   `UserProfiles` (Drift) хранит XP, но `SettingsService` (Hive) хранит состояние онбординга.
*   Ежедневные квесты хранятся в Hive, хотя достижения — в Drift.

**Риск:** Сложность обеспечения консистентности данных (например, при сбросе всех данных или восстановлении бэкапа) и риск повреждения данных при отсутствии единой транзакционной модели.

### 2.4 Хрупкая интеграция с ИИ
В `OpenRouterService` и `PriceAnalysisService` используется текстовый парсинг JSON-ответов от ИИ с помощью регулярных выражений или простого `json.decode` с ручной очисткой строк (`replaceAll('```json', '')`).

**Риск:** При малейшем изменении формата ответа нейросети приложение падает или выдает ошибку "ПОШКОДЖЕНИЙ КОНТРАКТ".

### 2.5 Дублирование кода в UI
Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` практически идентичны.
Виджеты распределения средств (`SplitSlider`) не масштабируемы для N-целей.

## 3. Анализ качества кода и покрытия тестами

*   **Linter:** Проект чист (осталось 11 информационных замечаний), что является хорошим показателем.
*   **Тесты:** В директории `test/` присутствует только один базовый `widget_test.dart`. Полностью отсутствует покрытие бизнес-логики (XP math, Streak logic, DB migrations).
*   **Атомарность:** Вызовы `bountyProvider.checkDeposit` и `questProvider.notifier.completeQuest` в `SavingsNotifier` происходят *вне* транзакции БД. Если они упадут, депозит будет записан, а прогресс геймификации — нет (или наоборот).

## 4. Рекомендации по рефакторингу (Phase 2)

1.  **N-Goals Migration:**
    *   Создать таблицу `DepositAllocations(deposit_id, goal_id, amount)`.
    *   Мигрировать данные из `Deposits` в новую таблицу.
    *   Унифицировать экраны настройки целей.
2.  **Декомпозиция SavingsNotifier:**
    *   Вынести XP-логику в `XpDomainService`.
    *   Вынести логику транзакций в `DepositRepository`.
    *   Использовать `SavingsNotifier` только как координатор.
3.  **Унификация хранилищ:**
    *   Перенести мета-данные геймификации (квесты, уведомления) из Hive в Drift для обеспечения транзакционной целостности.
4.  **Стабилизация AI:**
    *   Внедрить структурированный вывод (JSON Schema) и валидацию на стороне сервиса.
5.  **Тестирование:**
    *   Написать Unit-тесты для `XpService` и `StreakService`.
    *   Написать интеграционные тесты для миграций БД.
