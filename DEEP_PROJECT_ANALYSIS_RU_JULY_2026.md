# Глубокий технический анализ проекта PiggyVault (Июль 2026)

## 1. Введение
Данный отчет представляет собой комплексный аудит кодовой базы PiggyVault. Цель анализа — выявить архитектурные узкие места, технический долг и подготовить почву для реализации Фазы 2 (динамические цели, облачная синхронизация, социальные функции).

---

## 2. Архитектурный обзор

### 2.1 Управление состоянием (State Management)
Проект использует **Riverpod**.
- **Плюсы:** Реактивность, простота тестирования провайдеров.
- **Минусы:** Наблюдается чрезмерная концентрация бизнес-логики в `SavingsNotifier`.

### 2.2 Хранение данных (Storage)
Используется гибридная схема:
- **Drift (SQLite):** Реляционные данные (транзакции, цели, профиль).
- **Hive:** Ключ-значение (настройки, уведомления, еженедельные челенджи).
- **Проблема:** Отсутствие атомарности при обновлении данных в обеих системах одновременно.

### 2.3 Интеграция с ИИ
Реализована через `OpenRouterService` (DeepSeek).
- Используется для анализа цен и генерации советов от "Кибер-коуча".

## 3. Выявленный технический долг и проблемы

### 3.1 Проблема "N-Goals" (Критично 🚨)
Архитектура жестко завязана на существование ровно двух целей: `goal_a` и `goal_b`.
- **Где проявляется:**
    - `lib/data/database.dart`: Таблица `Deposits` содержит колонки `goalAAmount` и `goalBAmount`.
    - `lib/core/providers/savings_notifier.dart`: Логика распределения захардкожена на проценты между A и B.
    - `lib/data/backup_service.dart`: Экспорт в CSV/JSON ожидает только две цели.
    - UI: Экраны онбординга продублированы (`GoalASetupScreen` и `GoalBSetupScreen`).
- **Последствие:** Невозможно добавить 3-ю цель без переписывания ядра системы.

### 3.2 SavingsNotifier как "God Object" (Высокая важность ⚠️)
Метод `createDeposit` в `SavingsNotifier` занимает ~250 строк кода. Он отвечает за:
1. Запись в БД.
2. Расчет XP.
3. Расчет стритков (Streak).
4. Проверку ачивок.
5. Логику лутбоксов.
6. Обновление Squads.
- **Последствие:** Сложность тестирования и высокий риск багов при изменении любого из компонентов.

### 3.3 Дублирование кода (Средняя важность ⚠️)
- **Onboarding:** Экраны настройки цели А и Б практически идентичны.
- **Gamification:** Логика проверки достижений в `AchievementService` содержит хардкод ID целей (`halfway_ps5`, `ps5_acquired`).

### 3.4 Хрупкость парсинга ИИ (Средняя важность ⚠️)
В `PriceAnalysisService` и `BountyProvider` используется регулярное выражение или простой поиск подстроки для извлечения JSON из текстового ответа ИИ.
- **Риск:** Если модель ИИ изменит формат вступления (например, добавит вежливое приветствие), парсинг может сломаться.

## 4. Рекомендации по рефакторингу (Фаза 2)

### 4.1 Переход к динамическим целям (N-Goals)
1. **Схема БД:**
    - Удалить `goalAAmount`/`goalBAmount` из `Deposits`.
    - Создать таблицу `DepositAllocations { deposit_id, goal_id, amount }`.
2. **UI:** Объединить экраны настройки целей в один универсальный компонент.
3. **Logic:** Рефакторинг `SavingsNotifier` для итерации по списку аллокаций.

### 4.2 Декомпозиция сервисов
Вынести логику из `SavingsNotifier` в отдельные доменные сервисы:
- `XpCalculatorService`
- `StreakManagerService`
- `RewardEngineService` (объединяющий ачивки и бейджи)

### 4.3 Подготовка к Cloud Sync
1. **UUID:** Убедиться, что все таблицы используют UUID (сейчас `UserProfiles` использует `Int` по умолчанию).
2. **Таймстампы:** Добавить `updated_at` во все таблицы для разрешения конфликтов (Last Write Wins).

### 4.4 Стабилизация ИИ
Перейти на использование **Structured Output** (если поддерживается API) или внедрить более надежную валидацию схем JSON на стороне Dart (например, с использованием `json_serializable`).

---

## 5. Заключение
Проект PiggyVault имеет прочный фундамент и уникальный сеттинг (Cyberpunk/Gamification). Однако текущий "захардкоженный" подход к целям и перегруженность основного контроллера логикой станут барьером для масштабирования. Рекомендуется начать Фазу 2 с рефакторинга базы данных и распределения ответственности между сервисами.
