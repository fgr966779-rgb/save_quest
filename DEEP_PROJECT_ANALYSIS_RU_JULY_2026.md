# Глубокий технический анализ проекта PiggyVault (Июль 2026)

## 1. Общий статус проекта
Проект PiggyVault представляет собой развитую систему личных финансов с сильными элементами геймификации. Кодовая база структурирована по принципам Clean Architecture, что является хорошим показателем. Однако, проект достиг критической точки технического долга в своей основной архитектуре данных.

## 2. Анализ архитектуры и технологий
*   **Стек:** Flutter 3.6.2, Riverpod, Drift (SQLite), Hive.
*   **Качество кода:** Линтер настроен хорошо (осталось всего 11 информационных предупреждений).
*   **Тестирование:** Тестовое покрытие минимально (только базовые виджет-тесты), что создает риски при рефакторинге.

## 3. Критические архитектурные проблемы

### 🚨 3.1. Системный Hardcoding "N-Goals"
Вся система жестко завязана на существование ровно двух целей: `goal_a` и `goal_b`.
- **База данных:** Таблица `Deposits` содержит фиксированные колонки `goal_a_amount` и `goal_b_amount`.
- **Распространение:** В коде найдено **121 прямое упоминание** `goal_a` и `goal_b`.
- **Последствия:** Невозможность добавления 3-й цели без масштабного переписывания БД, логики распределения и UI. Это главный блокиратор масштабируемости.

### 🏛️ 3.2. SavingsNotifier (God Object)
Класс `SavingsNotifier` (`lib/core/providers/savings_notifier.dart`) нарушает принцип SRP (Single Responsibility Principle).
- **Обязанности:** Координация транзакций БД, расчет XP, логика Crit Hits, выпадение лутбоксов, стрик-менеджмент, проверка достижений.
- **Риски:** Высокая сложность метода `createDeposit` (~250 строк) делает его крайне хрупким. Ошибка в логике геймификации может привести к откату финансовой транзакции.

### 👯 3.3. Избыточность кода (DRY)
- **Onboarding:** Экраны `GoalASetupScreen` и `GoalBSetupScreen` дублируют друг друга на 95%.
- **Модели:** Наблюдается путаница между `Achievements` и `Badges`. Они работают параллельно, хотя по сути являются типами наград.

### 🤖 3.4. Хрупкость AI-интеграции
- **Парсинг:** Использование `_extractJson` (поиск `{` и `}`) в `PriceAnalysisService` и `OpenRouterService` ненадежно. Любое изменение в стиле ответа модели (например, добавление вводных слов) сломает функционал.

## 4. Рекомендации по развитию (Phase 2)

1.  **Рефакторинг БД (Приоритет №1):**
    - Внедрение таблицы `DepositAllocations (deposit_id, goal_id, amount)`.
    - Переход на UUID для всех таблиц (сейчас `UserProfiles` использует `id=1`).
2.  **Декомпозиция логики:**
    - Создание отдельных доменных сервисов: `XpService`, `StreakService`, `LootboxService`.
3.  **Синхронизация:**
    - Добавление полей `updated_at` и `is_deleted` (soft delete) во все таблицы для реализации стратегии "Last Write Wins" при интеграции с Firebase.
4.  **Унификация UI:**
    - Создание универсальных виджетов для настройки целей и отображения прогресса, которые не зависят от их количества.
