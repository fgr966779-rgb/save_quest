# Глубокий технический анализ проекта PiggyVault (Июль 2026)

## 1. Обзор архитектуры
Проект построен с использованием **Flutter** и следует принципам Clean Architecture (с некоторыми отступлениями).
- **State Management**: Riverpod (использование `StateNotifier` и `AsyncValue`).
- **Database**: Drift (SQLite) для реляционных данных и Hive для ключ-значение настроек.
- **Navigation**: GoRouter.

## 2. Критические архитектурные проблемы (Technical Debt)

### 2.1. "God Object" SavingsNotifier
Файл `lib/core/providers/savings_notifier.dart` содержит метод `createDeposit`, который берет на себя слишком много ответственностей (~250 строк кода):
- Управление транзакциями БД.
- Расчет XP и уровней.
- Логика стрик (streak) и заморозки.
- Обработка критических ударов (Critical Hits).
- Расчет наград Cyber-Market и баджей.
- Логика выпадения лутбоксов.
- Интеграция с квестами и баунти.

**Риск**: Крайне сложно тестировать и поддерживать. Любое изменение в логике геймификации может сломать процесс сохранения депозита.

### 2.2. Жесткое ограничение количества целей (N-Goals Debt)
Система жестко ограничена двумя целями: **Goal A** и **Goal B**.
- **База данных**: В таблице `Deposits` зашиты колонки `goalAAmount` и `goalBAmount`.
- **Хардкод ID**: Строки `goal_a` и `goal_b` встречаются в **16 файлах**.
- **UI**: Виджеты `DualProgressRing` и `SplitSlider` физически не могут отобразить более 2 целей.
- **Бизнес-логика**: `AchievementService` проверяет прогресс именно по этим ID (`halfway_ps5`, `ps5_acquired`).

**Риск**: Невозможность добавить 3-ю цель без переписывания половины приложения и миграции БД.

### 2.3. Фрагментация хранилища (Storage Fragmentation)
Данные распределены между **Drift** и **Hive**:
- Профиль, цели, депозиты — в Drift.
- Настройки, текущие квесты, баунти, локация — в Hive.

**Риск**: Отсутствие атомарности. Если транзакция в Drift пройдет успешно, а запись в Hive (например, завершение квеста) упадет, данные рассинхронизируются.

## 3. Проблемы реализации и качества кода

### 3.1. Дублирование кода (Code Duplication)
Экраны `lib/features/onboarding/screens/goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` практически идентичны (95% совпадения). Они различаются только провайдерами, в которые записывают данные, и текстами.

### 3.2. Хрупкая интеграция с ИИ (AI Fragility)
В `PriceAnalysisService` и `OpenRouterService` используется ручной парсинг JSON через `RegExp` и `indexOf/lastIndexOf`.
- Метод `_extractJson` ищет фигурные скобки.
- Метод `_toKopecks` делает агрессивную очистку строки.

**Риск**: Если модель ИИ вернет текст перед JSON или изменит формат, парсинг упадет с ошибкой или вернет неверные данные.

### 3.3. Тестируемость (Testability)
Большинство сервисов геймификации (`XpService`, `StreakService`, `AchievementService`) реализованы как классы со статическими методами. Это делает невозможным использование моков (mocking) при тестировании `SavingsNotifier` и других компонентов.

## 4. Рекомендации по рефакторингу (Phase 2)

1.  **N-Goals Refactor**:
    - Изменить схему БД: создать таблицу `DepositAllocations` (deposit_id, goal_id, amount).
    - Перевести UI на динамические списки целей.
2.  **Decoupling Gamification**:
    - Вынести расчеты XP, стрик и достижений из `SavingsNotifier` в отдельные доменные сервисы, которые будут вызываться через DI (Riverpod).
3.  **Consolidation**:
    - Объединить экраны настройки целей в один параметризуемый виджет.
4.  **Robust AI Parsing**:
    - Использовать структурированные схемы (например, через `json_serializable`) и более надежные методы обработки ответов от OpenRouter.
