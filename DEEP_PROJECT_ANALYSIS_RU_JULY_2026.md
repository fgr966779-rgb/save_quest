# Глубокий технический анализ проекта PiggyVault (Июль 2026)

## 1. Архитектурный обзор
Проект построен на современном стеке Flutter и следует принципам Feature-driven архитектуры с элементами Clean Architecture.

### Технологический стек:
*   **Фреймворк:** Flutter 3.6.2 (Dart 3.6).
*   **Управление состоянием:** Riverpod (StateNotifier, AsyncValue).
*   **База данных:** Drift (SQLite) для реляционных данных.
*   **Key-Value хранилище:** Hive для настроек и метаданных.
*   **Навигация:** GoRouter.
*   **AI:** Интеграция с OpenRouter (модели DeepSeek).

## 2. Ключевые проблемы и технический долг

### 2.1 Проблема "N-Goals" (Критично)
В текущей реализации система жестко ограничена поддержкой только двух целей (`goal_a` и `goal_b`). Это пронизывает все слои приложения:
*   **Database (`database.dart`):** Таблица `Deposits` имеет колонки `goalAAmount` и `goalBAmount`. Запросы в транзакциях явно обращаются к ID `goal_a` и `goal_b`.
*   **SavingsNotifier:** Метод `createDeposit` принимает `goalAPercent` и жестко рассчитывает доли для двух целей.
*   **BackupService:** Логика экспорта в CSV и импорта завязана на фиксированные имена и количество целей.
*   **UI:** Виджеты `DualProgressRing`, `SplitSlider` и экраны дашборда/онбординга спроектированы под дуальную модель.

### 2.2 SavingsNotifier как "God Object"
Класс `SavingsNotifier` в `lib/core/providers/savings_notifier.dart` берет на себя слишком много ответственности:
*   Управление транзакциями БД.
*   Расчет XP и уровней.
*   Логика стриков (серий).
*   Валидация достижений.
*   Генерация лутбоксов.
*   Взаимодействие с внешними провайдерами (Bounty, Quests).
*   *Риск:* Сложность тестирования и высокая вероятность багов при изменении любого из компонентов.

### 2.3 Фрагментация данных
Данные распределены между Drift и Hive без единого механизма обеспечения атомарности:
*   **Drift:** Цели, депозиты, профиль, достижения, скиллы, лутбоксы, питомцы, альянсы, квесты.
*   **Hive:** Настройки, состояние онбординга, история спинов, активные баунти, уведомления.
*   *Риск:* При сбое во время обновления "связки" (например, запись в Drift прошла, а в Hive — нет) состояние приложения может стать рассогласованным.

### 2.4 Хрупкость AI-интеграции
Сервисы `PriceAnalysisService` и `BountyProvider` полагаются на ручной парсинг JSON из текстовых ответов нейросети с помощью регулярных выражений или `indexOf`.
*   *Риск:* Любое изменение формата ответа AI (даже добавление вежливого вступления) приведет к отказу функций.

## 3. Дублирование кода

### 3.1 Онбординг
Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` практически идентичны. Они копируют логику валидации, оформления и работы с провайдерами. Это затрудняет внедрение динамического количества целей на этапе настройки.

### 3.2 Логика бэкапа
`BackupService` содержит огромные блоки ручного маппинга JSON для каждой таблицы Drift. При добавлении новой таблицы разработчик обязан вручную обновить методы импорта/экспорта в 3-4 местах, что чревато пропусками данных.

## 4. Рекомендации по рефакторингу (Фаза 2)

### 4.1 Динамические цели
1.  Создать промежуточную таблицу `DepositAllocations (deposit_id, goal_id, amount)`.
2.  Удалить `goalAAmount`/`goalBAmount` из `Deposits`.
3.  Перевести `SavingsNotifier` на работу с `Map<String, double>` (цель_id -> процент).

### 4.2 Декомпозиция логики
Вынести бизнес-правила из `SavingsNotifier` в отдельные Domain Services:
*   `XpDomainService`: расчеты опыта и уровней.
*   `StreakDomainService`: логика сохранения/сгорания серий.
*   `RewardDomainService`: выдача лутбоксов и ачивок.

### 4.3 Унификация Reward-системы
Объединить `Achievements` и `Badges` (которые сейчас хранятся в JSON профиля) в единую таблицу `Rewards` с типизацией.

### 4.4 Стабильность AI
1.  Использовать системные промпты для принудительного JSON-формата.
2.  Внедрить JSON-схемы для валидации ответов на стороне Dart.

---
**Итог:** Проект имеет отличную базу для геймификации, но требует серьезного архитектурного "выравнивания" перед внедрением социальных функций и облачной синхронизации.
