# Отчет по техническому аудиту проекта PiggyVault (Июль 2026)

## 1. Архитектурный анализ

### 1.1 Проблема "Божественного объекта" (God Object)
Основная бизнес-логика приложения сосредоточена в `SavingsNotifier` (`lib/core/providers/savings_notifier.dart`).
Этот класс отвечает за:
*   Создание транзакций (депозитов).
*   Обновление баланса целей.
*   Расчет XP и уровней.
*   Логику стриков (серий).
*   Валидацию достижений.
*   Управление лутбоксами.
*   Интеграцию с квестами и баунти.

**Риск:** Высокая связность (tight coupling) затрудняет тестирование и внесение изменений. Любая ошибка в расчете XP может заблокировать сохранение депозита.

**Рекомендация:** Декомпозировать `SavingsNotifier`, вынеся логику XP, стриков и достижений в отдельные доменные сервисы (частично начато в `lib/core/services/gamification/`). `SavingsNotifier` должен выступать только как координатор транзакции.

### 1.2 Жесткое кодирование целей (Goal A / Goal B)
По всему проекту (БД, UI, Notifiers) прослеживается жесткая привязка к двум целям: `goal_a` и `goal_b`.
*   В таблице `Deposits` есть колонки `goalAAmount` и `goalBAmount`.
*   В `AchievementService` проверки завязаны на ID `goal_a`/`goal_b`.
*   В Onboarding созданы два почти идентичных экрана для каждой цели.

**Риск:** Невозможность создания 3-й и более целей без масштабного переписывания кода.

**Рекомендация:** Реализовать систему N-целей. Использовать таблицу `DepositAllocations` для связи "многие-ко-многим" между депозитами и целями.

## 2. Анализ данных и синхронизации

### 2.1 Готовность к Cloud Sync
Текущая база данных (версия 8) не полностью готова к облачной синхронизации.
*   Отсутствуют поля метаданных: `updatedAt` (дата последнего изменения) и `isSynced` (флаг синхронизации).
*   Хотя UUID используется для многих сущностей, некоторые таблицы (например, `UserProfiles`) полагаются на фиксированные ID.

**Рекомендация:** Обновить схему БД до версии 9, добавив поля синхронизации во все таблицы.

### 2.2 Безопасность ключей
API-ключи (например, `openrouter_api_key`) хранятся в `SettingsService` через Hive.

**Рекомендация:** Использовать `flutter_secure_storage` для чувствительных данных.

## 3. Пользовательский интерфейс и дублирование

### 3.1 Дублирование экранов Onboarding
Экраны `GoalASetupScreen` и `GoalBSetupScreen` идентичны на 95%. Различаются только текстовые метки и провайдеры, в которые сохраняются данные.

**Рекомендация:** Объединить их в один параметризованный `GoalSetupScreen`.

### 3.2 Локализация (L10n)
Локализация реализована через статический Map в `l10n.dart` вместо стандартных ARB файлов.

**Риск:** Трудности при масштабировании на большое количество языков и невозможность использования стандартных инструментов Flutter для L10n.

## 4. AI Интеграция

### 4.1 Хрупкость парсинга (Fragile Parsing)
В `PriceAnalysisService` и `OpenRouterService` используется ручной парсинг JSON с помощью регулярных выражений и обрезки строк.

**Риск:** Если модель AI изменит формат ответа (например, добавит вступительный текст), парсинг упадет.

**Рекомендация:** Использовать структурированный вывод (JSON mode) от провайдера и надежные библиотеки для валидации схем (например, `json_serializable`).

## 5. План действий (Phase 2 Roadmap)

1.  **Консолидация Onboarding:** Устранение дублирования экранов.
2.  **Миграция БД (v9):** Подготовка к синхронизации и N-Goals.
3.  **Рефакторинг N-Goals:** Переход на динамическое распределение средств.
4.  **Декомпозиция SavingsNotifier:** Вынос геймификации в сервисы.
5.  **Внедрение Firebase:** Реализация Squads и Cloud Sync.
