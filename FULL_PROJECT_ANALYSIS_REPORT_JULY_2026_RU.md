# Полный отчет по анализу проекта - PiggyVault (Июль 2026)

## 1. Резюме
PiggyVault — это мобильное приложение для геймификации личных финансов на базе Flutter, которое успешно достигло этапа MVP (Фаза 1). Основной цикл «Депозит -> XP/Прогрессия -> Награды» полностью функционален. Однако проект сталкивается со значительными архитектурными «узкими местами», которые затруднят масштабирование во второй фазе (социальные функции и облачная синхронизация). Основные проблемы связаны с жестко закодированной логикой ровно для двух целей и централизованным координатором (God Object), который берет на себя слишком много обязанностей.

## 2. Технологический стек
- **Фреймворк:** Flutter 3.x
- **Управление состоянием:** Riverpod (StateNotifier, AsyncValue, StreamProvider)
- **База данных:** Drift (SQLite) для структурированных данных, Hive для настроек Key-Value и временных данных.
- **Интеграция ИИ:** OpenRouter (DeepSeek) для финансового коучинга и ежедневных миссий (bounties).
- **Архитектура:** Структура feature-first с попыткой реализации Clean Architecture (Core/Data/Features).

## 3. Детальный анализ компонентов

### 3.1 Слой данных (`lib/data/database.dart`)
- **Сильные стороны:** Использование UUID для большинства первичных ключей — отличное решение для будущей облачной синхронизации. Стратегия миграции хорошо документирована до версии 8.
- **Критический долг:** Таблица `Deposits` содержит жестко заданные поля `goalAAmount` и `goalBAmount`. Это корень проблемы невозможности создания N целей.
- **Недостающие функции:** Отсутствие колонок `updated_at` и `is_synced` во всех таблицах затруднит разрешение конфликтов при синхронизации с облаком.

### 3.2 Бизнес-логика (`lib/core/providers/savings_notifier.dart`)
- **Паттерн God Object:** `SavingsNotifier` координирует транзакции БД, расчет стриков, получение XP, повышение уровней, валидацию достижений, дроп лутбоксов и проверку ежедневных миссий.
- **Прогресс рефакторинга:** Часть логики (XP, стрики, достижения) была успешно вынесена в сервисы в `lib/core/services/gamification/`, но нотификатор по-прежнему выступает основным оркестратором.
- **Привязка к N-целям:** Метод `createDeposit` все еще принимает параметр `goalAPercent` и явно обновляет две жестко заданные цели.

### 3.3 Слой пользовательского интерфейса (UI)
- **Дублирование кода:** Экраны настройки целей в онбординге (`goal_a_setup_screen.dart` и `goal_b_setup_screen.dart`) идентичны примерно на 95%.
- **Специализация виджетов:** Виджеты, такие как `DualProgressRing` и `SplitSlider`, рассчитаны только на сравнение двух целей.
- **Локализация:** `lib/core/providers/l10n.dart` использует огромную жестко заданную карту (`Map`) вместо стандартных `.arb` файлов, что станет неуправляемым по мере роста приложения.

### 3.4 Интеграция ИИ
- **Хрупкий парсинг:** `BountyNotifier` и `PriceAnalysisService` полагаются на `indexOf('{')` и замену строк для извлечения JSON из ответов ИИ. Это не обеспечивает надежной валидации и соблюдения схемы.
- **Логика резервного копирования:** Высокая зависимость от статических каталогов при сбое ИИ или отсутствии API-ключей.

### 3.5 Социальные функции (Squads и Joint Goals)
- **Статус:** Реализованы UI и локальное хранилище.
- **Готовность к синхронизации:** Модели данных стабильны, но логика полностью локальна. Переход на синхронизацию в реальном времени (Firestore/Supabase) потребует значительного переписывания `JointGoalsProvider`.

## 4. Реестр технического долга

| Категория | Проблема | Влияние | Приоритет |
| :--- | :--- | :--- | :--- |
| **Архитектура** | Хардкод логики 2-х целей | Препятствует добавлению 3-й цели. | Критический |
| **Логика** | SavingsNotifier God Object | Высокий риск регрессий; сложность тестирования. | Высокий |
| **UI** | Дублирование в онбординге | Сложность поддержки; непоследовательный UX. | Средний |
| **Данные** | Отсутствие метаданных синхронизации | Блокирует облачную синхронизацию Фазы 2. | Высокий |
| **ИИ** | Хрупкий парсинг JSON | Частые сбои при обновлении моделей ИИ. | Средний |
| **Тесты** | Минимальное покрытие тестами | Низкая уверенность при рефакторинге. | Высокий |

## 5. Дорожная карта и рекомендации для Фазы 2

### 5.1 Немедленный рефакторинг (Шаг 1)
- **Миграция базы данных под N-целей:** Внедрить таблицу `DepositAllocations` и мигрировать существующие данные `goal_a/b`.
- **Генерализация виджетов:** Рефакторинг `SplitSlider` и `ProgressRings` для работы со списком `List<Goal>`.
- **Унификация онбординга:** Создать единый экран `GoalSetupScreen`, который можно вызывать несколько раз.

### 5.2 Подготовка к облачной синхронизации (Шаг 2)
- **Обновление схемы:** Добавить `updated_at` (DateTime) и `is_synced` (Boolean) во все таблицы.
- **UUID:** Убедиться, что `UserProfiles` и другие таблицы используют UUID.

### 5.3 Стабильность ИИ (Шаг 3)
- **Структурированный вывод:** Использовать извлечение JSON на основе регулярных выражений или специализированный промпт-инжиниринг.
- **Валидация схемы:** Внедрить слой валидации для сгенерированного ИИ JSON перед парсингом в модели.

### 5.4 Тестирование (Непрерывно)
- **Unit-тесты:** Реализовать тесты для `XpService`, `StreakService` и новой логики распределения депозитов.
- **Интеграционные тесты:** Проверить полный цикл депозита от UI до базы данных.
