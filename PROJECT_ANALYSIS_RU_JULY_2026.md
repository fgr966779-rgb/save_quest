# Глубокий технический анализ проекта PiggyVault (Июль 2026)

## 1. Резюме
Проект PiggyVault представляет собой зрелое Flutter-приложение с богатой функциональностью геймификации и кастомным дизайном в стиле киберпанк. Несмотря на высокую степень готовности фич, проект обременен значительным архитектурным долгом, который препятствует масштабированию (особенно переход к системе с неограниченным количеством целей) и усложняет поддержку.

---

## 2. Архитектурный обзор

### 2.1 Технологический стек
*   **Framework:** Flutter 3.6.2 (Stable).
*   **State Management:** Riverpod (с использованием `StateNotifier` и кодогенерации).
*   **Database:** Drift (SQLite) — основное хранилище; Hive — настройки и кэш.
*   **Navigation:** GoRouter.
*   **AI:** OpenRouter (DeepSeek V3/V4).
*   **Custom UI:** Активное использование `CustomPainter` и `flutter_animate`.

### 2.2 Структура проекта
Приложение следует feature-driven подходу, но некоторые модули (core/data) перегружены логикой, которая должна принадлежать конкретным фичам.

---

## 3. Критический технический долг

### 3.1 Hardcoded N-Goals (🚨 Самая высокая приоритетность)
Вся система жестко ограничена ровно двумя целями (`goal_a` и `goal_b`). Это ограничение прошито на всех уровнях:
*   **Database:** Таблица `Deposits` содержит фиксированные колонки `goalAAmount` и `goalBAmount`.
*   **Logic:** `SavingsNotifier.createDeposit` принимает фиксированные проценты распределения только для двух целей.
*   **UI:** Виджеты `DualProgressRing`, `SplitSlider` и экраны онбординга физически не поддерживают отображение 3+ целей.
*   **Services:** `AchievementService` и `BackupService` используют статические ID целей для расчетов и экспорта.

### 3.2 God Object: SavingsNotifier
Метод `createDeposit` в `lib/core/providers/savings_notifier.dart` нарушает принцип единственной ответственности (SRP):
*   Управляет транзакциями БД.
*   Рассчитывает математику XP и уровней.
*   Обрабатывает логику стриков.
*   Генерирует шансы критических ударов.
*   Управляет выпадением лутбоксов.
*   Проверяет достижения.
**Проблема:** Любое изменение в логике геймификации требует правки этого массивного метода (~250 строк), что повышает риск регрессий.

### 3.3 Дублирование кода (Onboarding)
Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` являются практически полными копиями друг друга. Это затрудняет внесение изменений в процесс настройки целей (нужно менять в двух местах).

## 4. Риски и недочеты

### 4.1 Хрупкость парсинга AI
Интеграция с `OpenRouter` реализована через текстовые промпты "Respond ONLY with JSON". Парсинг ответов в `BountyProvider` и `PriceAnalysisService` выполняется через примитивные операции со строками (`substring`, `replaceAll`).
*   **Риск:** Если AI добавит пояснительный текст или изменит формат, приложение упадет или перейдет на fallback-режим.

### 4.2 Фрагментация данных
Использование двух разных движков (Drift и Hive) для хранения персистентного состояния усложняет резервное копирование и синхронизацию.
*   **Пример:** `BackupService` вынужден вручную собирать данные из таблиц Drift и коробок Hive, что легко забыть обновить при добавлении новых данных.

### 4.3 Локализация (L10n)
Текущая реализация через `Map<String, Map<String, String>>` в `l10n.dart` неэффективна:
*   Нет поддержки плюрализации (множественных чисел).
*   Нет проверки ключей на этапе компиляции.
*   Сложно делегировать перевод внешним специалистам без доступа к коду.

### 4.4 Тестирование
Покрытие тестами близко к нулю. Учитывая сложность игровой экономики (XP, множители, лимиты), отсутствие unit-тестов для `XpService`, `StreakService` и миграций БД является критическим риском.

## 5. Рекомендации по рефакторингу (Фаза 2)

1.  **Миграция БД:**
    *   Создать таблицу `DepositAllocations(deposit_id, goal_id, amount)`.
    *   Удалить специфичные для целей колонки из `Deposits`.
2.  **Декомпозиция сервисов:**
    *   Выделить `XpDomainService`, `StreakDomainService` и `AchievementDomainService`.
    *   `SavingsNotifier` должен стать тонким координатором.
3.  **Консолидация UI:**
    *   Объединить экраны онбординга в один универсальный конструктор целей.
    *   Рефакторинг `SplitSlider` для поддержки динамического количества "ползунков" (или замена на список ввода долей).
4.  **Стабилизация AI:**
    *   Перейти на использование JSON-схем в промптах и использовать надежные библиотеки для валидации JSON (например, `json_serializable`).
5.  **Внедрение тестов:**
    *   Приоритет: Unit-тесты для всей бизнес-логики в `lib/core/services/gamification/`.
