# Глубокий анализ проекта PiggyVault (Июль 2026)

## 1. Введение
Данный отчет представляет собой комплексный анализ текущего состояния проекта PiggyVault. Проект прошел стадию MVP и обладает богатым функционалом в области гамификации и управления личными финансами, однако содержит ряд архитектурных ограничений, которые могут затруднить масштабирование во второй фазе разработки.

## 2. Архитектурный обзор
Проект построен на современном стеке технологий Flutter:
*   **Управление состоянием:** Riverpod (StateNotifier, AsyncValue).
*   **База данных:** Drift (SQLite) для реляционных данных.
*   **Локальное хранилище:** Hive для настроек и простых ключ-значение данных.
*   **Навигация:** GoRouter.
*   **ИИ-интеграция:** OpenRouter (DeepSeek) для финансовой аналитики.

## 3. Ключевые проблемы и узкие места

### 3.1. Проблема "N-Goals" (Хардкод целей)
Это самое критическое ограничение системы на текущий момент.
*   **Суть:** В таблице `Deposits` жестко заданы колонки `goalAAmount` и `goalBAmount`. В `SavingsNotifier` и многих UI-экранах логика завязана на существование ровно двух целей (`goal_a` и `goal_b`).
*   **Где обнаружено:** `lib/data/database.dart`, `lib/data/backup_service.dart`, `lib/features/dashboard/screens/dashboard_screen.dart`, `lib/features/onboarding/screens/`.
*   **Риски:** Невозможность добавить 3-ю цель или использовать приложение для одной цели без "костылей".

### 3.2. SavingsNotifier как "God Object"
Метод `createDeposit` в `lib/core/providers/savings_notifier.dart` разросся до ~250 строк.
*   **Суть:** Один метод отвечает за транзакции БД, расчет XP, логику стриков, выдачу наград, расчет лутбоксов и обновление конфига аватара.
*   **Риски:** Сложность тестирования, высокий риск регрессий при внесении изменений, нарушение принципа единственной ответственности (SRP).

### 3.3. Хрупкость интеграции с ИИ
*   **Суть:** `OpenRouterService` и `PriceAnalysisService` используют регулярные выражения (`_extractJson`) для парсинга ответов от ИИ.
*   **Риски:** Малейшее отклонение в формате ответа ИИ (например, лишний текст перед JSON) ломает функционал.

### 3.4. Фрагментация данных
*   **Суть:** Данные распределены между Drift (основные таблицы) и 5-ю разными боксами Hive (`milestones_box`, `notifications_box`, `settings` и т.д.).
*   **Риски:** Отсутствие атомарности при обновлении данных в разных хранилищах. Если запись в Drift прошла успешно, а в Hive упала — данные рассинхронизируются.

### 3.5. Дублирование кода в Onboarding
*   **Суть:** `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` практически идентичны.
*   **Риски:** Необходимость вносить правки в два места при изменении дизайна или логики настройки целей.

## 4. Технический долг в BackupService
Текущий `BackupService` требует ручного добавления каждой новой таблицы в методы экспорта/импорта. При рефакторинге N-Goals этот сервис придется полностью переписывать, так как он завязан на статичные ID целей.

## 5. Рекомендации по рефакторингу (Phase 2)

### 5.1. Переход на динамические цели
1.  Создать таблицу `DepositAllocations(deposit_id, goal_id, amount)`.
2.  Удалить `goalAAmount`/`goalBAmount` из `Deposits`.
3.  Обновить `SavingsNotifier` для итерации по списку аллокаций.

### 5.2. Декомпозиция логики гамификации
Вынести расчеты в отдельные доменные сервисы:
*   `XpDomainService` — только математика опыта.
*   `RewardEngine` — проверка условий достижений.
*   `StreakManager` — расчет состояния огня.
`SavingsNotifier` должен лишь координировать вызовы этих сервисов внутри транзакции.

### 5.3. Стабилизация ИИ
Использовать `response_format: { "type": "json_object" }` в запросах к OpenRouter (если поддерживается моделью) и внедрить типизированные DTO для ответов с использованием `json_serializable`.

### 5.4. Унификация Onboarding
Создать один универсальный `GoalSetupScreen`, который принимает параметры (индекс цели, цвет, заголовок) и может вызываться циклично в зависимости от выбранного количества целей.

## 6. Заключение
Проект PiggyVault имеет отличный потенциал благодаря глубокой проработке игровых механик. Однако для успешного внедрения облачной синхронизации и социальных функций (Squads) необходимо в первую очередь устранить жесткую привязку к двум целям и нормализовать структуру базы данных.
