# Глубокий анализ проекта PiggyVault (Июль 2026)

## 1. Введение
Проект PiggyVault представляет собой мобильное приложение для управления финансами с элементами геймификации, построенное на Flutter. На текущем этапе проект успешно прошел Фазу 1 и готовится к переходу к Фазе 2 (социальные функции и облачная синхронизация). Данный отчет содержит детальный анализ архитектуры, текущих проблем и технического долга.

---

## 2. Архитектурный обзор
*   **State Management:** Riverpod. Используется `StateNotifier` для управления состоянием.
*   **База данных:** Drift (SQLite). Реализована надежная работа с локальными данными, поддержка миграций и транзакций.
*   **Навигация:** GoRouter.
*   **Геймификация:** Развитая система XP, уровней, стриков, наград и скиллов. Логика распределена между сервисами в `lib/core/services/gamification/`.
*   **AI Интеграция:** Использование OpenRouter (модели DeepSeek) для анализа транзакций и цен.

---

## 3. Критические проблемы и технический долг

### 3.1. Проблема N-Goals (Жесткая привязка к двум целям) 🚨
Это самый серьезный архитектурный барьер для масштабирования.
*   **Где проявляется:**
    *   `AppDatabase`: Колонки `goalAAmount` и `goalBAmount` в таблице `Deposits`. Методы `saveDepositAndUpdateGoals` жестко используют ID 'goal_a' и 'goal_b'.
    *   `SavingsNotifier`: Метод `createDeposit` принимает `goalAPercent` и рассчитывает доли для двух целей.
    *   **UI:** Виджеты `DualProgressRing` и `SplitSlider` разработаны строго под две цели.
    *   `MilestoneService`: Ключи Hive для достижений захардкожены как 'goal_a_25' и т.д.
*   **Последствия:** Невозможность добавления 3-й и последующих целей без переписывания значительной части ядра.

### 3.2. SavingsNotifier как "Божественный объект" (God Object) ⚠️
Несмотря на вынос части логики в сервисы (XpService, StreakService), `SavingsNotifier` остается перегруженным.
*   **Проблема:** Он координирует транзакции БД, расчеты геймификации, проверку ачивок, запуск баунти и квестов.
*   **Рекомендация:** Дальнейшая декомпозиция. `SavingsNotifier` должен вызывать высокоуровневые "Use Cases", а не содержать всю логику координации внутри себя.

### 3.3. Дублирование UI (Onboarding) 👯‍♂️
*   **Проблема:** Файлы `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` практически идентичны (~95% совпадения кода).
*   **Рекомендация:** Объединить в один переиспользуемый `GoalSetupScreen`, принимающий конфигурацию (заголовок, цвет, индекс цели).

### 3.4. Хрупкий парсинг ответов AI 🤖
*   **Проблема:** `OpenRouterService` и `PriceAnalysisService` используют `_extractJson` через поиск индексов `{` и `}` и регулярные выражения для очистки данных.
*   **Риск:** Любое отклонение AI от ожидаемого формата JSON (например, добавление пояснительного текста внутри JSON или изменение структуры) приведет к сбоям.
*   **Рекомендация:** Использовать более надежные библиотеки для валидации схем (например, `zod`-подобные решения для Dart) или усилить промпты требованием структурированного вывода.

### 3.5. Локализация (L10n) 🌍
*   **Проблема:** Переводы хранятся в огромном Map внутри `l10n.dart`.
*   **Последствия:** Сложность поддержки при добавлении новых языков, отсутствие стандартных инструментов Flutter для работы с `.arb` файлами.

## 4. Готовность к облачной синхронизации (Phase 2)
Приложение требует доработки для поддержки синхронизации:
1.  **UUID:** Большинство таблиц используют UUID, но `UserProfiles` привязан к жесткому ID `1`.
2.  **Метки времени:** Необходимо добавить колонку `updated_at` во все таблицы для реализации стратегии "Last Write Wins".
3.  **isSynced:** Нужно добавить флаг `is_synced` для отслеживания локальных изменений, не отправленных в облако.

---

## 5. Резюме и рекомендации

1.  **Рефакторинг БД (Приоритет 1):** Переход на таблицу `DepositAllocations` (многие-ко-многим между депозитами и целями).
2.  **Унификация UI:** Создание универсальных виджетов для работы со списком целей.
3.  **Стандартизация L10n:** Переход на `.arb` файлы.
4.  **Укрепление AI-слоя:** Внедрение защищенного парсинга и обработки ошибок.
5.  **Очистка README:** Удаление устаревших упоминаний BLoC и Firebase (до их реального внедрения), актуализация текущего стека (Riverpod).
