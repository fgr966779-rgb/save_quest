# Project Audit & Analysis Report: PiggyVault (June 2026)

## 1. Executive Summary
PiggyVault has successfully transitioned beyond its MVP stage, establishing a robust local-first foundation with a unique cyberpunk aesthetic and gamified core. However, the current architecture faces a "Scalability Wall" due to a hardcoded 2-goal limitation and a high-complexity state management layer. Transitioning to Phase 2 (Social & Cloud) requires significant structural decoupling.

## 2. Architectural Analysis

### 2.1 State Management (Riverpod)
*   **The God Object:** `SavingsNotifier` (~350 lines) is the central bottleneck. It handles database transactions, streak math, XP calculation, lootbox rolls, and achievement validation in a single monolithic `createDeposit` method.
*   **Reactivity:** High dependency on `ref.watch` in the Dashboard leads to frequent re-renders.

### 2.2 Data Layer (Drift & Hive)
*   **Relational (Drift):** Currently at schema version 8. Primary tables like `Deposits` are hardcoded with `goalAAmount` and `goalBAmount`, preventing the addition of a 3rd goal.
*   **Key-Value (Hive):** Used for settings, milestones, and notifications. `MilestoneService` uses hardcoded Hive keys (e.g., `goal_a_25`), creating a secondary layer of goal dependency.
*   **Cloud Sync Readiness:** Low. Tables lack `updatedAt` timestamps and use `Int` auto-increment IDs for `UserProfiles`, which will cause collisions in a multi-device environment.

### 2.3 AI Integration (OpenRouter / DeepSeek)
*   **Stability:** Parsing logic in `PriceAnalysisService` relies on regex-based JSON extraction from LLM strings, which is prone to failure if the model deviates from the prompt.
*   **Personality Engine:** Well-implemented `CoachPersonality` system, but insights are currently ephemeral and not stored for long-term behavioral analysis.

## 3. Technical Debt & Scaling Blockers

### 3.1 The "N-Goals" Blockade
A search reveals over 120 hardcoded references to `goal_a` and `goal_b` across:
*   **Database Schema:** `Deposits` table columns.
*   **Onboarding:** Redundant `GoalASetupScreen` and `GoalBSetupScreen`.
*   **UI Components:** `DualProgressRing`, `SplitSlider`.
*   **Services:** `AchievementService`, `MilestoneService`, `BackupService`.
*   **Analytics:** `AnalyticsScreen` explicitly calculates percentages for exactly two goals.

### 3.2 Backup & Portability
*   `BackupService` performs manual, typed serialization for every table. Adding a new table requires updates in three places (Export, Restore, Insert).
*   CSV Export is hardcoded to a 2-column goal format.

### 3.3 Social & Joint Goals
*   **Current State:** UI-complete but logic-empty. Shared goals and members are stored in local Drift tables.
*   **The Gap:** No networking layer (Firebase/Supabase) or CRDT-lite logic for handling concurrent updates from multiple users.

## 4. UI/UX Inconsistencies
*   **Onboarding:** The flow is rigid and prevents users from adding more or fewer than exactly 2 goals during setup.
*   **Localization:** `AppLocalizations` uses a hardcoded Map. While fast, it complicates external translation workflows (standard ARB files).

## 5. Strategic Recommendations for Phase 2

### 5.1 Immediate Refactoring (Infrastructure)
1.  **N-Goals Migration:**
    *   Create `DepositAllocations` (deposit_id, goal_id, amount).
    *   Deprecate hardcoded columns in `Deposits`.
2.  **Domain Decomposition:**
    *   Split `SavingsNotifier` into `XpEngine`, `StreakEngine`, and `RewardEngine`.
3.  **UUID Transition:**
    *   Migrate all primary keys to UUID to support offline-first cloud sync.

### 5.2 Social & Networking
1.  **Firebase Integration:** Move `Squads` and `JointGoals` to Firestore.
2.  **Real-time Feed:** Implement a global event bus for social notifications.

### 5.3 AI Enhancements
1.  **Structured Outputs:** Switch to JSON-mode prompts or use a more robust schema validation library for AI responses.
2.  **Behavioral Analysis:** Implement a `MoodService` to track user sentiment towards saving over time.
