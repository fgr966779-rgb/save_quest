# Deep Project Analysis: PiggyVault (June 2026)

## 1. Architectural Overview
The project follows a modular structure, separating core logic, data persistence, and feature-specific components. It utilizes **Riverpod** for state management and **Drift (SQLite)** for the primary relational database.

### 1.1 Key Components
- **State Management**: Heavy reliance on Riverpod providers.
- **Persistence**: Hybrid approach using **Drift** for complex relational data (Transactions, Goals, Profiles) and **Hive** for simple key-value pairs (Settings, Notifications, Daily Bonus).
- **Navigation**: **GoRouter** is used for declarative routing.
- **AI Integration**: **OpenRouter (DeepSeek)** powers financial insights and dynamic bounty missions.

## 2. Technical Debt & Critical Bottlenecks

### 2.1 The "God Object": `SavingsNotifier`
The `SavingsNotifier.createDeposit` method is a significant architectural bottleneck (~250 lines). It handles:
- Currency conversion.
- Database transactions.
- Streak logic calculation.
- XP & Leveling math.
- Lootbox drop rolls.
- Achievement validation.
- External provider updates (Bounties, Quests).

**Recommendation:** Decompose into domain services (e.g., `XpService`, `StreakService`, `LootboxService`) to improve testability and maintainability.

### 2.2 Schema Bottleneck: Hardcoded N-Goals
The `Deposits` table in `database.dart` currently has hardcoded columns `goalAAmount` and `goalBAmount`. This strictly limits the app to exactly two goals and makes scaling to "N-Goals" impossible without a major migration.

**Status:** Critical blocker for Phase 2.
**Proposed Fix:** Replace with a `DepositAllocations` table (1-to-N relationship).

### 2.3 Fragmented Persistence
Persistence is split between Drift and 5+ Hive boxes. While this works, it creates "Sync Hell" for Phase 2 (Cloud Sync). Cross-store transactions (e.g., updating a Drift profile and a Hive notification box simultaneously) are not atomic.
