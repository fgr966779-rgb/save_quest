# Подробный технический анализ проекта PiggyVault (Июль 2026)

## 1. Введение
Данный отчет представляет собой результаты глубокого аудита кодовой базы PiggyVault. Анализ проводился с целью выявления архитектурных ограничений, технического долга и подготовки фундамента для Фазы 2 разработки.

---

## 2. Архитектурный обзор
Проект построен на базе **Flutter** с использованием следующих ключевых технологий:
*   **State Management:** Riverpod.
*   **Persistence:** Drift (SQLite) для реляционных данных и Hive для настроек.
*   **Navigation:** GoRouter.
*   **AI Integration:** OpenRouter (модели DeepSeek).

### Выявленная структура:
*   `lib/core`: Общие сервисы, провайдеры и UI-компоненты.
*   `lib/data`: Слой данных (БД, Backup, Settings).
*   `lib/features`: Функциональные модули (геймификация, онбординг, дашборд).

---

## 3. Критические проблемы и технический долг

### 3.1. Жесткое ограничение количества целей (Pervasive Goal Hardcoding)
**Описание:** Логика приложения жестко завязана на две цели: `goal_a` и `goal_b`.
*   **БД (`database.dart`):** Таблица `Deposits` содержит колонки `goalAAmount` и `goalBAmount`.
*   **Бизнес-логика (`savings_notifier.dart`):** Транзакции обновления баланса явно ищут записи по ID `goal_a`/`goal_b`.
*   **UI:** Виджеты `DualProgressRing`, `SplitSlider` и экраны онбординга не поддерживают динамическое количество целей.
*   **Риск:** Невозможность добавить 3-ю цель без переписывания значительной части проекта.

### 3.2. "Божественный объект" (God Object) в SavingsNotifier
**Описание:** Метод `SavingsNotifier.createDeposit` (~250 строк) выполняет слишком много задач:
1.  Управление транзакцией БД.
2.  Расчет XP и уровней.
3.  Логика стриков (серий дней).
4.  Генерация лутбоксов.
5.  Обновление достижений.
*   **Риск:** Сложность тестирования, высокая вероятность багов при изменении одного из компонентов геймификации.

### 3.3. Дублирование кода (Code Duplication)
**Описание:** Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` являются практически идентичными копиями.
*   **Риск:** Повышенные затраты на поддержку. Любое изменение в дизайне онбординга нужно вносить в оба файла.

### 3.4. Хрупкий парсинг ответов ИИ
**Описание:** `PriceAnalysisService` и `OpenRouterService` используют `indexOf('{')` и регулярные выражения для извлечения JSON из текстовых ответов DeepSeek.
*   **Риск:** Если ИИ изменит формат ответа (например, добавит вводный текст или изменит ключи), парсинг упадет.

### 3.5. Фрагментация данных
**Описание:** Настройки пользователя хранятся в Hive, в то время как профиль пользователя (XP, уровень) — в Drift.
*   **Риск:** Отсутствие атомарности при обновлении данных, которые могут быть логически связаны.

## 4. Стратегия рефакторинга (Phase 2)

### 4.1. Переход к N-Goals (Динамические цели)
1.  **Миграция БД:**
    *   Создать таблицу `GoalAllocations(deposit_id, goal_id, amount)`.
    *   Удалить фиксированные колонки из `Deposits`.
2.  **Абстракция UI:**
    *   Заменить `DualProgressRing` на `MultiGoalProgress`.
    *   Заменить `SplitSlider` на компонент динамического распределения долей.

### 4.2. Декомпозиция SavingsNotifier
*   Вынести логику в доменные сервисы: `XpCalculator`, `StreakManager`, `RewardEngine`.
*   `SavingsNotifier` должен только координировать вызовы этих сервисов внутри транзакции.

### 4.3. Унификация онбординга
*   Создать универсальный `GoalSetupScreen`, который принимает параметры цели (индекс, заголовок, описание) и сохраняет данные в список.

### 4.4. Улучшение работы с ИИ
*   Использование `JsonSchema` (если поддерживается провайдером) или внедрение надежной валидации схем на стороне Dart (например, с помощью `json_annotation`).

---

## 5. Заключение
Проект PiggyVault обладает богатым функционалом геймификации, но страдает от архитектурных ограничений "быстрого старта". Рефакторинг по направлению N-Goals и декомпозиция бизнес-логики являются критически важными шагами перед масштабированием или внедрением облачной синхронизации.
