# Подробный технический анализ проекта PiggyVault (Июль 2026)

## 1. Обзор архитектуры
Проект представляет собой мобильное приложение на Flutter, использующее современные подходы к разработке, но имеющее ряд критических архитектурных ограничений, которые необходимо устранить перед масштабированием (Фаза 2).

### Технологический стек:
*   **Ядро:** Flutter 3.6.2 (Dart 3.x).
*   **Управление состоянием:** Riverpod (использование `StateNotifier` и `AsyncValue`).
*   **Хранение данных:**
    *   **Drift (SQLite):** Реляционная БД для транзакций, целей, профиля и гамификации.
    *   **Hive:** Ключ-значение хранилище для настроек и кэша уведомлений.
*   **Навигация:** GoRouter.
*   **AI-интеграция:** OpenRouter (DeepSeek) для финансовой аналитики и квестов.

## 2. Ключевые проблемы и технический долг

### 2.1 "God Object" — SavingsNotifier
Файл `lib/core/providers/savings_notifier.dart` содержит метод `createDeposit`, который занимает около 250 строк.
**Проблема:** Внутри одной транзакции перемешаны:
*   Запись в БД.
*   Математика XP.
*   Логика стриков (StreakService).
*   Логика уровней.
*   Проверка ачивок (AchievementService).
*   Ролл лутбоксов.
*   Обновление аватара и кредитов.
**Риск:** Высокая сложность тестирования и риск нарушения атомарности при добавлении новых функций.

### 2.2 Жесткое ограничение "Две цели" (N-Goals Debt)
Архитектура жестко завязана на существование ровно двух целей: `goal_a` и `goal_b`.
*   **БД:** В таблице `Deposits` есть колонки `goalAAmount` и `goalBAmount`.
*   **Логика:** `SavingsNotifier` и `AchievementService` обращаются к целям по захардкоженным ID.
*   **UI:** Виджеты `DualProgressRing` и `SplitSlider` рассчитаны только на две цели.
*   **Резервное копирование:** `BackupService` содержит специфичную логику для сопоставления этих двух целей в CSV/JSON.

### 2.3 Дублирование кода в Onboarding
Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` идентичны на 95%. Различаются только ключи провайдеров и текстовые метки. Это создает лишний код и усложняет поддержку.

### 2.4 Хрупкая интеграция с ИИ
Сервисы `OpenRouterService` и `PriceAnalysisService` используют текстовые промпты "Respond ONLY with JSON" и ручной парсинг через regex или `indexOf('{')`.
**Риск:** Если ИИ добавит вводный текст или изменит структуру, приложение упадет или не сможет обработать данные.

### 2.5 Фрагментация данных
Использование двух разных движков БД (Drift и Hive) затрудняет реализацию облачной синхронизации. Нет единого механизма отслеживания изменений (`updatedAt`) во всех таблицах.

## 3. Анализ компонентов

### 3.1 Система гамификации
Реализована глубоко: есть дерево навыков (Skill Tree), классы персонажей (Hacker, Magnate, Resilience), система лутбоксов и аватаров. Однако логика начисления XP разбросана между сервисами и нотификаторами.

### 3.2 Дистанционное управление (Remote Server)
В проекте есть отдельный Node.js сервер (`remote_server/`), позволяющий управлять ПК через WebSocket. Это интересная мета-функция, но она требует безопасности (сейчас используется простой SHA-256 challenge-response).
