# Детальный отчет по анализу проекта PiggyVault (Июль 2026)

## 1. Обзор архитектуры
Проект представляет собой мобильное приложение на Flutter, ориентированное на геймифицированное управление личными финансами.

### Технологический стек:
*   **State Management:** Riverpod (используются StateNotifierProvider, Provider, StreamProvider).
*   **Database:** Drift (SQLite) для структурированных данных и Hive для Key-Value настроек и простых кешей.
*   **Навигация:** GoRouter с использованием ShellRoute для базового интерфейса.
*   **Геймификация:** Собственные сервисы для XP, стрик-системы, достижений и системы классов.
*   **Интеграция с AI:** OpenRouter (DeepSeek) для генерации квестов (Bounties) и анализа цен.

## 2. Глубокий анализ технического долга

### 2.1 Проблема "N-Goals" (Критическая)
Текущая архитектура жестко завязана на существование ровно двух целей: "Goal A" и "Goal B".
*   **База данных (`database.dart`):** Таблица `Deposits` содержит колонки `goalAAmount` и `goalBAmount`. Таблица `Goals` используется, но логика в коде обращается к ней по жестко заданным ID `goal_a` и `goal_b`.
*   **Логика (`savings_notifier.dart`):** Метод `createDeposit` принимает `goalAPercent`, рассчитывает доли для двух целей и выполняет обновление `goal_a` и `goal_b` напрямую в транзакции.
*   **UI:** Виджет `SplitSlider` и экраны онбординга (`GoalASetupScreen`, `GoalBSetupScreen`) физически разделены и поддерживают только две сущности.
*   **Риск:** Добавление 3-й цели потребует изменения схемы БД и переписывания ~40% бизнес-логики.

### 2.2 God Object: `SavingsNotifier`
Класс `SavingsNotifier` выполняет слишком много задач:
1.  Управление транзакциями в БД.
2.  Расчет XP и уровней.
3.  Логика стриков (серий дней).
4.  Валидация достижений.
5.  Генерация лутбоксов.
6.  Взаимодействие с провайдерами квестов (Bounties).
*   **Последствие:** Сложность тестирования и высокий риск регрессий при любых изменениях.

### 2.3 Дублирование и избыточность кода
*   **Onboarding:** Экраны `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart` идентичны на 95%. Разница лишь в заголовках и провайдерах, в которые сохраняются данные.
*   **Achievements vs Badges:** В системе сосуществуют "Достижения" (в БД) и "Значки" (внутри JSON-конфига аватара), что создает путаницу в источниках данных.

### 2.4 Хрупкая интеграция с AI
В `BountyProvider` и `PriceAnalysisService` используется метод `_extractJson` (поиск `{` и `}` в строке).
*   **Проблема:** ШИ иногда может возвращать некорректный JSON или добавлять пояснительный текст вне скобок, что ломает парсинг. Отсутствует строгая схема валидации ответа.

### 2.5 Локализация (`l10n.dart`)
Все переводы хранятся в огромной Map внутри Dart-файла.
*   **Проблема:** Это затрудняет работу профессиональных переводчиков и увеличивает размер бинарного файла. Отсутствует поддержка стандартных `.arb` файлов.

## 3. Состояние геймификации и внешних функций
*   **Skill Tree:** Реализовано хорошо, есть разделение на ветки Hacker, Magnate, Resilience.
*   **Squads (Альянсы):** Реализован UI и локальное хранение, но отсутствует реальный сетевой слой для взаимодействия между пользователями.
*   **Remote Control:** Интересная, но слабо связанная с основным финтех-функционалом фича. Работает через WebSocket напрямую к ПК.

## 4. Рекомендации по рефакторингу (Фаза 2)

### Шаг 1: Переход к N-Goals (Динамические цели)
1.  **Схема БД:** Создать таблицу `DepositAllocations(deposit_id, goal_id, amount)`. Убрать специфичные колонки для целей из таблицы `Deposits`.
2.  **Logic:** Переписать `createDeposit`, чтобы он принимал `Map<String, double> allocations` (ID цели -> Процент/Сумма).
3.  **UI:** Объединить экраны настройки целей в один универсальный `GoalSetupScreen`, который можно вызывать в цикле.

### Шаг 2: Декомпозиция `SavingsNotifier`
1.  Вынести расчет XP в `XpService`.
2.  Вынести расчет уровней в `LevelingService`.
3.  Использовать `Domain Events` для уведомления систем достижений и квестов о совершенном депозите, вместо прямой связи.

### Шаг 3: Улучшение AI-парсинга
1.  Внедрить проверку JSON по схеме.
2.  Улучшить промпты, добавив One-Shot примеры для стабилизации формата ответа.

### Шаг 4: Покрытие тестами
*   Необходимо написать Unit-тесты для `XpService` и `StreakService`, так как это ядро мотивации пользователя. Сейчас в проекте только базовый `widget_test.dart`.

---
**Итог:** Проект имеет отличную визуальную составляющую и богатый функционал, но требует глубокого структурного рефакторинга перед добавлением новых крупных фич (облачная синхронизация, мульти-аккаунты).
