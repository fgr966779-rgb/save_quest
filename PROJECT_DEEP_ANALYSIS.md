# Глубокий анализ проекта PiggyVault (Июнь 2026)

## 1. Резюме
Проект PiggyVault представляет собой геймифицированное приложение для управления личными финансами в киберпанк-стилистике. На данный момент проект успешно завершил Фазу 1 (MVP) и обладает богатым функционалом: система уровней, древо навыков, AI-баунти, терминал и локальное хранилище. Однако архитектура содержит критические "бутылочные горлышки", которые будут препятствовать масштабированию в Фазе 2 (Социальные функции и Cloud Sync).

## 2. Архитектурный обзор

### 2.1 State Management (Riverpod)
*   **Использование:** Приложение активно использует Riverpod для управления состоянием и внедрения зависимостей.
*   **Проблема:** Логика сильно сконцентрирована в `SavingsNotifier`. Он выполняет роль "Божественного объекта" (God Object), смешивая управление транзакциями БД, расчет XP, логику стриков, генерацию лутбоксов и валидацию достижений.

### 2.2 Слой данных (Drift & Hive)
*   **Drift (Relational):** Используется для основных транзакций, профиля и игровых сущностей. Схема версии 8.
*   **Hive (Key-Value):** Используется для настроек, уведомлений и квестов.
*   **Риск:** Фрагментация данных между двумя хранилищами создает риски нарушения атомарности. Например, обновление квестов в Hive происходит вне транзакции Drift.

## 3. Анализ проблем и технического долга

### 3.1 Хардкод N-Goals (Критично)
*   **Текущее состояние:** Таблица `Deposits` содержит жестко заданные колонки `goalAAmount` и `goalBAmount`.
*   **Последствия:** Невозможно добавить третью цель или реализовать динамическое распределение средств без изменения схемы БД и всего связанного кода (от UI до аналитики).

### 3.2 Дублирование UI (Onboarding)
*   **Файлы:** `goal_a_setup_screen.dart` и `goal_b_setup_screen.dart`.
*   **Проблема:** Экраны практически идентичны. Любое изменение в дизайне или валидации требует двойной работы и повышает риск ошибок.

### 3.3 Атомарность транзакций
*   **SavingsNotifier:** Методы `checkDeposit` (Bounty) и `completeQuest` вызываются *после* завершения транзакции БД. Если приложение упадет между этими вызовами, данные рассинхронизируются (деньги сохранятся, но опыт за квест не будет начислен).

### 3.4 Готовность к облачной синхронизации (Cloud Sync)
*   **ID:** Большинство таблиц используют UUID, но `UserProfiles` использует `Int` (ID=1). Это создаст конфликты при объединении данных нескольких профилей.
*   **Метаданные:** Отсутствуют колонки `updated_at` и `version` во многих таблицах, что необходимо для реализации стратегии "Last Write Wins" или CRDT.

### 3.5 Технический долг в BackupService
*   **Хардкод таблиц:** Список таблиц для бэкапа и восстановления прописан вручную. При добавлении новой таблицы (например, `DepositAllocations`) разработчик легко может забыть обновить сервис бэкапа.
*   **Хардкод целей в CSV:** Экспорт и импорт CSV жестко завязаны на существование двух целей (`goal_a`, `goal_b`). Это делает функционал несовместимым с системой N-Goals.

## 4. Рекомендации по рефакторингу (Стратегия Фазы 2)

### Шаг 1: Миграция на динамические цели (N-Goals)
1.  Создать таблицу `DepositAllocations(id, deposit_id, goal_id, amount)`.
2.  Перенести данные из `goalAAmount/goalBAmount` в новую таблицу.
3.  Удалить жесткие ссылки на цели в `SavingsNotifier` и `DepositScreen`.

### Шаг 2: Декомпозиция SavingsNotifier
1.  Выделить `XpDomainService`, `StreakDomainService` и `AchievementDomainService`.
2.  Передать управление бизнес-логикой этим сервисам, оставив `SavingsNotifier` только роль координатора.

### Шаг 3: Унификация Onboarding
1.  Создать единый `GoalSetupScreen`, принимающий параметры (index, totalSteps).
2.  Использовать его в `GoRouter` для любого количества начальных целей.

### Шаг 4: Подготовка к Cloud Sync
1.  Добавить `updatedAt` (DateTime) во все таблицы.
2.  Перевести `UserProfiles.id` на UUID (или использовать UID из Firebase Auth).

### Шаг 5: Рефакторинг BackupService
1.  Сделать процесс бэкапа более динамичным (итерирование по всем таблицам БД).
2.  Переписать логику CSV для поддержки произвольного количества целей.

## 5. Заключение
Проект имеет отличную визуальную базу и глубокую геймификацию. Устранение указанного технического долга в начале Фазы 2 позволит беспрепятственно внедрить социальные функции (Squads, Joint Goals) и надежную синхронизацию данных.
