# Отчёт о комплексном исследовании и анализе проекта PiggyVault

**Дата:** Июль 2026
**Статус проекта:** Завершена Фаза 1 (MVP), Подготовка к Фазе 2 (Social & Cloud Sync)

---

## 1. Резюме проекта
**PiggyVault** — это мобильное приложение для управления сбережениями с глубокими элементами геймификации в стиле киберпанк. Приложение позволяет пользователям откладывать деньги на цели, зарабатывать опыт (XP), повышать уровни, развивать дерево навыков и взаимодействовать с AI-коучем.

## 2. Анализ архитектуры

### 2.1 Технологический стек
- **Ядро:** Flutter 3.6.2 / Dart 3.x
- **Управление состоянием:** Riverpod (активно используются `StateNotifier` и генераторы).
- **База данных:** Drift (SQLite) для структурированных данных и Hive для настроек и уведомлений.
- **AI:** Интеграция с OpenRouter (модель DeepSeek) для анализа цен и генерации диалогов.

### 2.2 Структура данных (Drift)
Текущая версия схемы БД: **8**.
- Приложение использует UUID для большинства записей, что является отличным фундаментом для будущей синхронизации.
- **Проблема масштабируемости:** Таблицы `Deposits` и `Goals` имеют жесткую связь "один к двум", что ограничивает функционал приложения.

## 3. Выявленные проблемы и технический долг

### 3.1 Ограничение "N-Goals" (Критично)
Архитектура заблокирована на использовании ровно двух целей (`goal_a` и `goal_b`). Это прослеживается на всех уровнях:
- **БД:** Колонки `goalAAmount` и `goalBAmount` в таблице транзакций.
- **Notifier:** Метод `createDeposit` принимает один процент распределения, подразумевая наличие только двух целей.
- **UI:** Дублирование экранов онбординга и жесткая верстка слайдеров распределения.

### 3.2 SavingsNotifier (God Object)
Класс `SavingsNotifier` взял на себя слишком много обязанностей:
- Управление транзакциями БД.
- Расчет игровой логики (XP, Стрики, Криты).
- Выдача наград и лутбоксов.
- Валидация достижений.
*Рекомендация:* Декомпозиция логики в специализированные сервисы (`XpService`, `StreakService` и т.д.).

### 3.3 Хрупкость AI-сервисов
Парсинг ответов от OpenRouter реализован через поиск текстовых вхождений и регулярные выражения. Это создает риск падения приложения при изменении формата ответа моделью.

### 3.4 Дублирование кода (DRY)
- Экраны `GoalASetupScreen` и `GoalBSetupScreen` практически идентичны.
- Локализация реализована через `Map<String, Map<String, String>>`, что затрудняет поддержку при добавлении новых языков и большого объема текста.

## 4. Готовность к Фазе 2 (Social & Cloud)

### 4.1 Облачная синхронизация
- **Готовность:** 60%.
- **Нужно сделать:** Добавить колонки `updatedAt` и `isSynced`, заменить инкрементальный ID в `UserProfiles` на UUID, внедрить механизм разрешения конфликтов (Last-Write-Wins).

### 4.2 Социальные функции (Squads)
- **Готовность:** 20% (только UI и локальные таблицы).
- **Нужно сделать:** Внедрение Firebase/Supabase для работы в реальном времени, создание серверных триггеров для уведомлений внутри отряда.

## 5. Итоговые рекомендации

1.  **Рефакторинг N-Goals:** Это приоритет №1. Без перехода на динамические списки целей дальнейшее масштабирование бессмысленно.
2.  **Унификация UI:** Объединение дублирующихся экранов настройки целей в один универсальный компонент.
3.  **Стандартизация L10n:** Переход на использование официального инструментария Flutter Intl (`.arb` файлы).
4.  **Усиление AI-парсинга:** Внедрение типизированных DTO для обработки ответов от AI и механизмов повторных запросов при ошибках парсинга.
