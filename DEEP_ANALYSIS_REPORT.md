# Глибокий аналіз проекту PiggyVault

## 1. Огляд архітектури
Проект побудований на сучасному Flutter-стеку з чітким розділенням на шари, але з ознаками швидкої ітеративної розробки, що призвело до певного технічного боргу.

### Технологічний стек:
*   **Державне управління (State Management):** Riverpod з використанням генерації коду.
*   **База даних:**
    *   **Drift (SQL):** Основне сховище для профілів, цілей, транзакцій та розблокованих навичок/досягнень.
    *   **Hive (Key-Value):** Використовується через `SettingsService` для конфігурацій, щоденних квестів та AI-баунті.
*   **Навігація:** GoRouter.
*   **UI Екосистема:** Кастомні неонові віджети, анімації `flutter_animate`, робота з `CustomPainter`.

## 2. Виявлені проблеми та технічний борг

### 2.1 Монолітний "God Method" у `SavingsNotifier`
Метод `createDeposit` в `lib/core/providers/savings_notifier.dart` став занадто великим і складним. Він відповідає за:
1.  Конвертацію валют.
2.  Запис транзакції в БД.
3.  Оновлення балансів цілей.
4.  Розрахунок стріків.
5.  Розрахунок XP та рівнів.
6.  Нарахування кібер-кредитів.
7.  Розрахунок специфічного XP навичок (Hacker/Magnate/Resilience).
8.  Логіку випадіння лутбоксів.
9.  Перевірку та розблокування досягнень.
10. Оновлення конфігурації аватара.
11. Тригери для квестів та баунті.

**Рекомендація:** Розбити метод на окремі сервіси (напр., `GamificationEngine`, `StreakManager`), зберігаючи атомарність через транзакції Drift.

### 2.2 Хардкод ідентифікаторів цілей
Логіка в багатьох місцях (SavingsNotifier, UI екрани, Аналітика) жорстко прив'язана до двох цілей з ID `'goal_a'` та `'goal_b'`. Це унеможливлює створення користувачем 3-ї або більше цілей без переписування коду.

**Рекомендація:** Узагальнити логіку для роботи з динамічним списком цілей.

### 2.3 Дублювання систем винагород
В проекті існують дві паралельні системи:
*   **Achievements (`Achievement`):** Зберігаються в Drift, мають категорії рідкості, перевіряються в `SavingsNotifier`.
*   **Badges (`BadgeDef`):** Зберігаються як JSON в полі `avatarConfig` профілю користувача, перевіряються через `checkNewBadges`.

Вони часто дублюють умови (наприклад, стріки 7/14/30 днів є і там, і там).

**Рекомендація:** Об'єднати в єдину систему досягнень з уніфікованим сховищем у БД.

### 2.4 Фрагментація даних
Дані про квести та баунті зберігаються в Hive (через `SettingsService`), тоді як основний профіль — у Drift. Це ускладнює підтримку цілісності даних (наприклад, нарахування XP за квест вимагає ручного оновлення профілю в Drift після зміни стану в Hive).

## 3. Аналіз кодової бази (Linter & Health)
*   **Deprecated API:** Велика кількість попереджень щодо `withOpacity`. Рекомендується перехід на `withValues`.
*   **Стиль коду:** Багато конструкторів не використовують `super_parameters`, що є стандартом сучасного Dart.

---

## 4. Пріоритетний план рефакторингу

1.  **Phase A (Health):** Автоматичне виправлення лінтів через `dart fix` та заміна `withOpacity`.
2.  **Phase B (Decoupling):** Винесення логіки гейміфікації з `SavingsNotifier` в окремі класи.
3.  **Phase C (Unification):** Міграція бейджів у таблицю досягнень Drift.
4.  **Phase D (Genericity):** Рефакторинг UI та БД для підтримки довільної кількості цілей.
